# 005 — фазы загрузки и точные упакованные частоты

Дата: 2026-09-20. Ветка `perf/rechprav-load-phases`. Техническая синтетика,
без реальной истории Handy. Принято: готовая таблица `.rpf` для следующих
локальных опытов. Медиана загрузки B2 уменьшилась на 34.45%, resident RSS —
на 43.53 MiB; все значения, предсказания и метрики сохранены. Обновление SHA2
ради ускорения отклонено по результатам отдельного сравнения.

## Последовательность гипотез

1. `199b402`: раздельное измерение чтения, SHA256, decode, проверок trie.
   Сначала найдены реальные затраты, без изменения форматов или scorer.
2. `d809677`: опыт с `sha2 0.11.0` вместо `0.10.9`; добавлены независимые
   тестовые векторы и стабильное hex-кодирование digest. Гипотеза ускорения
   не получила убедительного подтверждения.
3. `dde352b`: возврат Cargo.toml/lock к прежним зависимостям; готовая частотная
   таблица с бинарным поиском вместо разбора TSV/BTreeMap при каждом запуске.
   TSV сохранён как эталон, обе реализации сравниваются в одном бинарнике.

Внешний формат словаря `.rpt`, генератор, защита, нормализация и scoring B2
не менялись. Параметры взяты из 003, подгонки по gold не было.

## Где уходило время

Три новых процесса исходного варианта, `before/`, медиана загрузки 3.853 s:

| Фаза | Медиана, ms |
|---|---:|
| Чтение `.rpt` | 63.50 |
| SHA256 всего `.rpt` для manifest | 875.73 |
| Внутренний checksum `.rpt` | 841.05 |
| UTF-8 и алфавит словаря | 138.73 |
| Структура и соответствие написаний путям trie | 413.59 |
| Чтение TSV | 10.85 |
| SHA256 TSV | 152.34 |
| Разбор TSV и построение частотного BTreeMap | 1414.51 |

Основные затраты — два прохода SHA256 по словарю и разбор TSV. Структурная
проверка сама по себе занимает заметно меньше. Вложенные `dictionary.validation.*`
уже входят в `dictionary.decode`; складывать их повторно нельзя. Медианы
фаз также не обязаны суммироваться в медиану общего времени. `resource_load_ms`
включает уничтожение временных буферов, внутренний `total` заканчивается раньше.

## SHA2: результат отрицательный для этой гипотезы

| Три процесса, TSV | sha2 0.10.9 | sha2 0.11.0 |
|---|---:|---:|
| Загрузка, min–max, s | 3.704–4.011 | 3.297–3.767 |
| Медиана загрузки, s | 3.853 | 3.717 |
| Медиана SHA256 всего словаря, ms | 875.73 | 814.47 |
| Медиана внутреннего checksum, ms | 841.05 | 802.95 |

Диапазоны перекрываются, серии запускались последовательно, не вперемешку;
трёх процессов недостаточно для вывода о небольшом ускорении. Меньше стал и
неизменённый разбор TSV, что также указывает на вариацию условий VM. Это
недостаточное подтверждение выигрыша, а не доказательство равной скорости.
Миграция только ради startup не принята, lock возвращён к 0.10.9.

В VM Xeon E5-2678 v3 отсутствуют CPU flags `sha`/`sha_ni`; есть AVX2.
В документации [sha2 0.11.0](https://docs.rs/sha2/0.11.0/sha2/)
ускорение AVX2 относится к SHA-512; SHA-256 на этом CPU использует software
fallback. Новая версия сама по себе не добавляет SHA-инструкции процессору.
Вариант [asm-hashes](https://github.com/RustCrypto/asm-hashes) просмотрен,
но не собран и не измерен: репозиторий архивирован, а README ограничивает
поддержку Windows/MSVC. Его скорость не оценивалась; вариант отложен.

Первая сборка с 0.11 обнаружила несовместимость `LowerHex` у результата digest.
Добавлен общий код lowercase hex и независимые SHA256-векторы из CPython hashlib:
пустой вход, границы padding/block и потоковые chunks. Они прошли с обеими
версиями и оставлены после возврата зависимости. Детали обновления:
[официальный changelog](https://github.com/RustCrypto/hashes/blob/master/sha2/CHANGELOG.md).

## Готовые частоты: контролируемое сравнение

Два профиля на одном commit `dde352b`, одинаковый `.rpt`, SHA2 0.10.9 и B2.
Различается только `[frequency].path`: исходный TSV / готовый `.rpf`.
Три новых процесса на вариант, перемешанный порядок с seed=505:
packed, tsv, tsv, packed, tsv, packed. Кеш ОС не очищался.
В каждом процессе — 100 повторений прежних 27 записей после прогрева.

| Показатель | TSV + BTreeMap | `.rpf` |
|---|---:|---:|
| Загрузка, три запуска, s | 3.518 / 3.673 / 3.567 | 2.338 / 2.195 / 2.591 |
| Медиана загрузки, s | 3.567 | 2.338 |
| Медиана frequency.decode, ms | 1326.33 | 163.39 |
| Медиана resident RSS процесса, MiB | 189.75 | 146.21 |
| Наибольший peak RSS, MiB | 210.35 | 146.23 |
| Медиана per-run warm analyze p95, ms | 0.630 | 0.679 |
| Размер частотного файла, MiB | 20.93 | 21.49 |
| Метрики корпуса | 5 TP / 0 FP / 10 FN | Точно те же |

Новый `frequency.decode` включает checksum и проверку таблицы. Таблица чуть
больше TSV на диске, но не требует аллокации строки/узлов дерева на каждый ключ.
Ускорение warm analyze не получено: p95 нового варианта 0.652–0.817 ms против
0.619–0.652 ms у TSV. Возможен небольшой штраф бинарного поиска по UTF-8;
отделить его от вариации VM этот опыт не позволяет. Оба варианта укладываются
в прежний инженерный ориентир p95≤5 ms на короткой синтетике.

Startup≤1 s не выполнен. В принятом варианте только SHA256 всего словаря и
его внутренний checksum занимают по медианам 750.76 и 686.63 ms. Проверки
целостности, формата и путей trie сохранены. Ускорение за счёт их отключения
не проверялось. Задержка реальной Handy, cold disk и Windows не измерялись.

## Эквивалентность и проверки

- Offline builder проверил все **661 389** нормализованных ключей и точные биты
  `f64` относительно TSV; сборка с проверкой/записью заняла 2.406 s.
- `.rpf`: 22 530 646 байт,
  SHA256 `689c7de7c863d3aedb9a3fa1094a95bc1af6575a20e2900d87c29563fe953695`.
  Исходный TSV: `b825e97778693cb7e3b5cb26d058ba6bde6cf4971471dc0a6f2d1a1e889c160f`.
- В каждой серии `predictions.jsonl` и `metrics.json` побайтно совпали с B2 full
  из 003. Корпус: `7a6b3d4fc2fd6d9d83ff28811f8ac9e6438a0589ff8ea655936084ec50307714`.
  Это 27 искусственных примеров; совпадение не оценивает качество на реальном ASR.
- 56 тестов прошли. Новые проверки: точность значений/оценок, пропуск и ноль,
  е/ё, бинарный поиск и отсутствующие ключи, усечённые/повреждённые файлы,
  ошибки структуры после пересчёта checksum, CLI и запрет перезаписи.
- clippy `--all-targets -D warnings`, rustfmt, offline release bin/examples,
  Python py_compile прошли. Fingerprints исторических запусков сверены с их
  commit, финальных — с текущим кодом. Исходный пользовательский план не изменён.

## Решение и следующий этап

Принять `.rpt` + `.rpf` как рабочий профиль следующих опытов; хранить TXT/TSV
и эталонные реализации для проверки. Сохранить SHA2 0.10.9. Весь scorer остаётся
экспериментальным, автоматическая вставка в Handy не включается.

Дальнейшее снижение startup пока отложить: для интерактивной интеграции отдельно
проверить процесс, загружающий ресурсы один раз, вместе с таймаутами/ошибками.
Следующий ограниченный опыт 006 — технические цели: отдельно различить защитный
domain и разрешённые кандидаты, сделать фиксированный технический набор с
правильными словами и неоднозначностями, проверить добавление целей при прежних
порогах. Сначала OOV; real-word и compound требуют своих опытов. Затем отдельно
distance=2/weighted edits. Не подгонять одновременно словарь, scorer и пороги.

## Воспроизведение и артефакты

Ресурсы взяты из опыта 003, лицензии и сборка описаны в
[resource-sources.md](../../../docs/rechprav/resource-sources.md).
Словарь `.rpt` тот же, что в 004. Для новых файлов/каталогов выбрать свободное имя:

```bash
~/.local/bin/cargo build --manifest-path rechprav/Cargo.toml --release --locked --offline --examples --bin rechprav
rechprav/target/release/rechprav build-frequency rechprav/artifacts/opencorpora-wordfreq/frequency.tsv --output rechprav/artifacts/opencorpora-wordfreq/frequency.rpf
python3 rechprav/scripts/run_load_experiment.py rechprav/experiments/my-load-run --profile tsv=rechprav/configs/opencorpora-packed-b2.toml --profile packed=rechprav/configs/opencorpora-packed-frequency-b2.toml
```

Если `.rpf` уже существует, шаг сборки пропустить. Исходные конфиги используются
из `rechprav/configs/`; снимки TOML внутри результатов сохраняют пути относительно
оригинальных конфигов и не предназначены для самостоятельного запуска оттуда.
Ранние серии воспроизводятся на своих commit; в них warm repetitions=1,
поэтому их warm latency не используется для сравнения с финальной серией.
