# 018: проверенный профиль и атомарная публикация

Дата: 2026-09-22. Ветка `feat/rechprav-profile-publication`.
Протокол: `5773314`, реализация: `5a83e18` (исходники чистые при запуске).

```bash
python3 rechprav/scripts/run_publication_experiment.py rechprav/experiments/018-profile-publication
```

## Результат

Rust заново строит профиль из вложенных manual/events/decisions/bindings и
проверяет его совпадение с экспортом 017. Node/SQLite хранит запрос, точные байты,
результат проверки, активное поколение и receipt. Новый запрос отменяет старую
незавершённую сборку. Ошибка новой сборки сохраняет прежний активный снимок.

| Шаг сквозного опыта | Desired | Active | Результат |
|---|---:|---:|---|
| Принят и опубликован composed | 1 | 1 | Точные байты 017 |
| Запрошены older и затем disable | 3 | 1 | older отклонён |
| Опубликован disable | 3 | 3 | Полностью выключенный профиль |
| Запрошен профиль с неверным config hash | 4 | 3 | Отказ, прежний active сохранён |
| Повтор publish initial | 4 | 3 | Старый receipt, без повторного включения |
| Новое осознанное восстановление composed | 5 | 5 | Содержимое равно поколению 1 |

18 Node-тестов прошли. Шесть реальных SIGKILL: после INSERT, перед COMMIT и после
COMMIT для request и publish. После reopen выполнен integrity_check; до commit
виден старый профиль, после — целый новый; потерянный ответ допускает повтор.
Читатели существующего и нового соединения видят старый целый снимок во время
незавершённой записи. Проверены конкурентные CAS, одинаковые запросы/публикации,
новая заявка во время Rust validation, повреждённая база, лимиты, scope,
неверный UTF-8, чужая SQLite и неизвестная schema.

Подменённые report/config с обновлёнными output hashes отклонены повторной сборкой.
Отдельно проверены изменение решения accept→reject с пересчитанным hash,
невалидный TOML, изменённый hash compiled source, неверные входы/environment,
действительное изменение временного словаря после формирования пакета.

135 Rust-тестов, clippy all-targets с `-D warnings`, fmt check, offline release
build нового валидатора и py_compile runner прошли. Capture-тесты 016 не повторяли:
их код не менялся. Rust runtime и composer binaries побайтно совпадают с 017.

## Контроль коррекций

Два опубликованных профиля прочитаны из базы и проверены на прежних 20 synthetic/dev
строках. 40 prediction records и оба metrics.json побайтно равны 017.

| Профиль | TP | FP | FN |
|---|---:|---:|---:|
| composed | 7 | 1 | 1 |
| global-off | 0 | 0 | 8 |

Это контроль сохранности поведения, не новый результат качества ASR. Неизменны
FP буквального упоминания и FN isolated «долгождать». Результаты не использовались
для подбора весов/порогов.

## Что исправлялось при проверке

Первый запуск тестов: 15/17 прошли, два теста были подготовлены неверно. В маленьком
manual отсутствовало обязательное `sets`; пересериализация manifest через JS JSON
меняла числа `1.0`→`1` и достигала resource guard раньше проверки подменённого
report. Исправлены данные, сохранены точные числовые представления при мутации
нужных hashes. Оба целевых теста затем прошли. Добавлен отдельный тест фиксации
байтов независимо от последующих изменений объекта вызывающей стороны; финально
18/18. Код хранилища и валидатора из-за этих двух ошибок не менялся.
Это дефекты тестовой подготовки, а не неудачные алгоритмы коррекции.

## Решение и границы

Принять SQLite-публикацию для экспериментального контура. Самодельные locks/rename
и проверка одних hashes не реализовывались как конкурирующие алгоритмы: отказ от
них — проектное решение, не результат измерения их скорости/надёжности.

База находится в ignored artifacts; точный путь сохранён в environment.json.
JSON snapshots/receipts/requests, исходные bundles, benchmark outputs и test logs
сохранены здесь. Рабочий сервер, его конфиги/БД, first-plan не изменялись; сеть
не использовалась. Снимки содержат только разрешённые технические примеры.

SIGKILL не проверяет потерю питания/носителя. Словари остаются внешними: проверены
при валидации, но не закреплены в памяти будущего reader. Следующий этап 019:
загрузка engine с проверкой ресурсов и публикация engine+generation одной заменой,
ошибки/reload со старым engine, запоздавшие загрузки и запросы, начатые до reload.
UI и работающий сервер подключать после этого опыта.
