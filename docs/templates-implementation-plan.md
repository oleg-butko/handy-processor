# План: шаблоны, двойное нажатие Win и вставка в исходное окно

Статус: реализация по этапам с отдельными коммитами. Основная платформа — Windows.

1. **Согласованное поведение**

   - Вкладка «Шаблоны» располагается между «Список правил» и «Настройки».
   - Двойное нажатие Win показывает окно и выбирает «Шаблоны». Если окно уже
     открыто, выбирается эта вкладка без пересоздания окна или редактора.
   - Справа сверху находятся запись хоткея, включение/выключение и интервал
     двойного нажатия в миллисекундах. Начальное значение — 200 мс; его можно
     увеличивать. Одиночный Win при включённом хоткее не открывает «Пуск».
   - По умолчанию видны все строки и все три уровня. Переключатели 1/2/3
     одновременно определяют видимые уровни и область поиска.
   - «Копировать» и «Вставить сразу» всегда используют третий уровень,
     независимо от переключателей. Кнопки — иконки с подсказками и aria-label.

2. **Что уже есть в коде**

   - `ui/src/App.tsx`: Mantine Tabs с `keepMounted`. Нужно сделать выбранную
     вкладку управляемым состоянием и добавить `TemplatesPage`.
   - `launcher/src-tauri/src/main.rs`: показ, фокусировка и скрытие одного окна;
     закрытие уже скрывает окно в tray. Есть проверка origin у native-команды.
   - `ui/src/launcher-bridge.ts`: мост React → Rust, пока для экспорта истории.
   - `src/app.ts`, `src/runtime-config.ts`: HTTP API и общий каталог runtime.
   - В соседнем Handy `src-tauri/src/shortcut/handy_keys.rs` обрабатывает
     нажатия/отпускания через `handy-keys`; `shortcut/tauri_impl.rs` содержит
     второй механизм глобальных сочетаний. Готовой логики двойного Win нет.
   - Handy `clipboard.rs` и `input.rs` реализуют Clipboard + Ctrl+V, задержки
     и платформенные коды клавиш. В Windows используется VK_V, что важно при
     русской раскладке. `paste_tx/` дополнительно решает восстановление буфера
     после чтения. Возврат из окна выбора шаблонов в прежнее поле нужно
     реализовать отдельно.

3. **Первый этап — проверить двойной Win на Windows**

   Это основной технический риск. Одиночный Win открывает «Пуск», а Win+другая
   клавиша запускает системное сочетание. Простое наблюдение за двумя
   нажатиями даст лишнее открытие «Пуска» и может потерять исходное окно.

   Предлагается небольшой Windows-модуль на Win32 API (`windows` crate),
   с `WH_KEYBOARD_LL` на отдельном потоке с циклом сообщений. В callback —
   только обработка состояния клавиш и отправка коротких сообщений; никаких
   файловых операций, ожиданий HTTP или вызовов React. Windows может удалить
   слишком медленный hook: [LowLevelKeyboardProc](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelkeyboardproc).

   Отдельный автомат распознавания принимает код клавиши, down/up и время
   события. Два нажатия обязательно разделены отпусканием. Автоповтор при
   удержании, чужие клавиши и собственные синтетические события не должны
   образовывать двойной тап. Для определения интервала предлагается сравнивать
   начало первого и второго нажатий: `delta <= threshold`; показ окна —
   после отпускания второй клавиши, если жест не превратился в сочетание.

   По уточнению пользователя одиночный Win подавляется: отложенный запуск
   «Пуска» и воспроизведение одиночного нажатия не нужны. Win+другая клавиша
   отменяет двойной тап. Системные сочетания по возможности проходят обычным
   путём, без задержки и переотправки всей последовательности. Для одиночного
   Win подавляется действие меню при отпускании. Проверить отсутствие залипания
   модификаторов и поведение Win+E/D/R/L, Shift+Win+S на Windows.

   Предлагаемый смысл «Win» — два нажатия одной и той же физической клавиши:
   LeftWin или RightWin. LeftWin → RightWin не образует двойное нажатие.
   При записи пользователь сможет указать конкретную сторону.

   Состояние жеста сбрасывается при изменении настроек, блокировке сеанса,
   смене внешнего окна между нажатиями и начале операции вставки. Завершение
   программы должно корректно освобождать hook и не оставлять клавиши нажатыми.
   Во время записи нового хоткея действие текущего временно приостанавливается.

4. **Показ вкладки и сохранение цели вставки**

   При первом потенциальном Win сохранить внешнее foreground-окно, PID и,
   когда доступно, информацию о фокусе GUI-потока. При подтверждении жеста
   проверить, что цель ещё актуальна. Захват после показа окна будет слишком
   поздним — foreground уже станет Handy Processor.

   Rust хранит `pendingTab = templates` и идентификатор запроса, показывает
   окно и отправляет событие React. После готовности интерфейс также запрашивает
   pending-состояние и подтверждает обработку. Это предотвращает потерю события
   при запуске или перезагрузке WebView. Повторный вызов, пока окно активно,
   не должен заменять внешнюю цель собственным окном Handy Processor.

   События выбора вкладки не должны размонтировать голосовой редактор.
   При уходе с его вкладки нужно явно деактивировать контекст диктовки,
   поскольку `keepMounted` оставляет компонент в памяти.

5. **Файл шаблонов и API**

   Источник — `templates.txt` в runtime-каталоге
   рядом с `config.json`, UTF-8 с поддержкой BOM, LF и CRLF. Пустые строки
   пропускаются. Строка содержит ровно три непустые части, разделённые двумя
   символами `>`; пробелы по краям частей убираются, внутренний текст сохраняется.
   Ошибочные строки показываются с номерами и причиной; исходный файл не меняется.
   Буквальный `>` и многострочные шаблоны требуют отдельного соглашения формата.

   Серверный модуль `src/templates.ts` отвечает за чтение, проверку и кэш.
   API `GET /api/templates` возвращает три уровня, исходный номер строки,
   версию загруженного файла и диагностику. Источник один: пользовательский
   файл, без параллельной копии содержимого в SQLite.

   Предусмотреть выбор файла в лаунчере, показ текущего пути и «Обновить».
   API чтения использует настроенный источник, а не произвольный путь из URL.
   Настроенный путь хранить в серверных настройках SQLite; их единственный
   владелец — Node-сервер. Выбор другого файла идёт через native-диалог, после
   чего сервер проверяет формат и сохраняет путь; при ошибке сохраняется прежний
   источник. Изменения настроек API проверяют origin и формат запроса.
   Браузер не сможет сам получить произвольный локальный путь через file input.

   При ошибке чтения или неполной внешней перезаписи сохраняется последняя
   удачная версия с видимым предупреждением. Установка и обновление приложения
   не должны перезаписывать пользовательский файл. Ожидаемый объём — 100–200
   строк: обычного списка React достаточно, виртуализация и поисковый индекс
   не нужны. Добавить разумный предел размера файла для обработки ошибок выбора.

6. **Поиск и React-интерфейс**

   `TemplatesPage` содержит блок уровней, строку запроса, 33 кнопки русского
   алфавита включая «ё», точку, удаление последнего символа и очистку.
   Кнопки букв редактируют запрос в позиции курсора, с учётом выделения.

   Предлагаемые правила поиска:

   - Без запроса видны все корректные строки в порядке файла.
   - Включено любое непустое подмножество уровней; по умолчанию 1+2+3.
   - Регистр не учитывается; для поиска предлагается приравнять «ё» к «е»,
     сохраняя оригинальное написание при отображении и копировании.
   - Запрос делится точками на префиксы; пустой фрагмент после точки игнорируется.
   - Для каждого префикса нужно найти хотя бы одно слово в выбранных уровнях.
     Между префиксами действует И, порядок слов не важен.
   - Например, `сл.др` совпадает со строкой
     `сложные задачи > другие варианты > готовый ответ`, если выбраны уровни
     1 и 2; при выборе только уровня 3 эта строка не совпадает.
   - Ищутся начала отдельных слов, а не подстроки внутри слов или только начало
     всего уровня. Границы слов должны учитывать Unicode и пунктуацию.
   - Подсвечиваются только совпавшие префиксы в видимых уровнях. Диапазоны
     пересечений объединяются; React выводит текстовые узлы и `<mark>`, без HTML
     из файла и без выполнения пользовательского регулярного выражения.

   Правый блок действий строки остаётся на месте при скрытии уровней.
   При повторном открытии вкладки предлагается сохранять уровни и запрос,
   фокусировать фильтр и выделять его текст для быстрого нового поиска.

7. **Копирование и «Вставить сразу»**

   Копирование записывает исходный третий уровень без автоматического пробела,
   Enter или применения правил обработки диктовки. В лаунчере используется
   native clipboard, в браузере — Clipboard API с обработкой ошибок.

   Вставка выполняется одной последовательной Rust-операцией:

   1. Проверить native-вызов, выбранную запись и наличие актуальной внешней цели.
   2. Записать третий уровень в буфер; при ошибке оставить окно открытым.
   3. Скрыть Handy Processor и запросить активацию сохранённого окна.
   4. Дождаться подтверждения foreground и отпускания модификаторов, с конечным
      таймаутом. Небольшая дополнительная пауза допускается, но не заменяет проверку.
   5. Повторно проверить цель и отправить Ctrl+V с кодом VK_V; освободить все
      синтетически нажатые клавиши даже при ошибке.
   6. Исключить повторный клик и автоматическую повторную отправку Ctrl+V:
      отсутствие подтверждения текста не означает, что вставки не было.

   Если цель закрылась или фокус не вернулся, не отправлять Ctrl+V в случайное
   окно. Оставить текст в буфере и показать результат «Скопировано; вставьте
   вручную». При обычном открытии через tray, когда достоверной цели нет,
   автоматическую вставку не предлагать.

   Предлагается после вставки оставлять шаблон в буфере. Это устраняет гонку
   раннего восстановления прежнего содержимого. Если требуется сохранять
   прежний буфер, отдельно адаптировать механизм Handy `paste_tx` с контролем
   владения буфером; чтение буфера само по себе ещё не доказывает вставку в
   нужное поле.

   Ограничения Windows: активация чужого окна может быть отклонена
   ([SetForegroundWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setforegroundwindow));
   ввод в приложение с более высоким уровнем привилегий блокируется UIPI
   ([SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput)).
   Foreground HWND не идентифицирует конкретный HTML-input в браузере: точное
   сохранение поля/каретки зависит и от целевого приложения.

8. **Разделение кода и этапы реализации**

   - Чистый автомат жеста — `launcher/src-tauri/src/double_tap.rs`, тестируется
     и на Linux через существующий `--no-default-features --lib`.
   - Windows hook, цель и вставка — отдельные платформенные модули; они
     подключаются только для Windows desktop-сборки.
   - Интеграция окна, native-команд и событий — `main.rs`, `launcher-bridge.ts`.
   - Файл и API — `src/templates.ts`, `src/app.ts`, тесты парсера и маршрутов.
   - Вкладка и поиск — `TemplatesPage.tsx`, отдельные чистые функции поиска,
     `App.tsx`, стили в существующей системе Mantine.
   - Настройки хоткея принадлежат лаунчеру и сохраняются между перезапусками;
     ошибка новой привязки не должна уничтожать предыдущую рабочую настройку.
   - В браузере остаются файл/поиск/копирование. Настройки глобального хоткея и
     вставка требуют Windows-лаунчер; Linux-часть приложения продолжает собираться.

   Порядок: файл и поиск с тестами → React-вкладка → автомат двойного нажатия
   и настройки → Windows-hook и вставка → интеграционные проверки и документация.
   Каждый этап сохраняется отдельным Conventional Commit.

9. **Проверки и критерии готовности**

   Автоматические тесты: пороги T−1/T/T+1, удержание и автоповтор, тройной тап,
   разные Win, посторонняя клавиша, смена окна и настроек, синтетические события;
   BOM/CRLF, пустые и повреждённые строки, Unicode, выбранные уровни, И по
   префиксам и точные диапазоны подсветки; копирование скрытого третьего уровня;
   потеря фокуса, закрытая цель, повторный клик и ошибка clipboard.

   В Windows вручную проверить Блокнот, браузерный input/textarea,
   VS Code, Word и используемые пользователем программы; две раскладки;
   закрытое в tray, открытое и свёрнутое окно; одновременную работу Handy;
   Win+E/D/R/L, Shift+Win+S; отмену, блокировку/разблокировку и перезапуск.
   Windows-тесты с настоящими окнами обязательны: Linux unit-тесты и headless
   Chromium не подтверждают работу глобального hook и возврат фокуса Windows.

   Ожидаемая надёжность: высокая у парсинга/поиска/копирования; подтверждаемая
   прототипом у двойного Win и системных сочетаний; зависимая от приложения у
   точного возврата в прежнее поле. Процент успеха без испытаний не заявляется.

10. **Допущения для первой реализации**

    - Настройки интервала ограничены разумным диапазоном, например 50–2000 мс,
      с начальным значением 200 мс. Это предлагаемый диапазон, а не ограничение ОС.
    - Пустые уровни считаются ошибкой; символ `>` внутри уровня и многострочные
      шаблоны не поддерживаются в первой версии.
    - После вставки в буфере остаётся шаблон. Восстановление прежнего буфера
      можно добавить отдельной настройкой, если оно понадобится.
    - Из других клавиш первая версия поддерживает записанный одиночный
      модификатор или клавишу; поддержка двойных сочетаний не требуется для
      согласованного двойного Win и может быть расширена отдельно.
