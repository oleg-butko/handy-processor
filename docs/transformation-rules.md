# Правила трансформации

## Пользовательская модель

Web UI содержит две вкладки: **История** и **Список правил**. На вкладке правил
каждое правило можно независимо включить или выключить. Изменение сохраняется
сразу и применяется к следующим запросам Handy; существующая история не
пересчитывается.

Текущий каталог:

| Стабильный ID | Название | По умолчанию |
| --- | --- | --- |
| `case.lowercase` | Нижний регистр | включено |
| `numbers.ru-cardinals-to-digits` | Русские числительные → цифры | включено |
| `punctuation.remove-final-period` | Удаление конечной точки | включено |

Распознавание русских числительных регистронезависимо. Поэтому его можно
использовать без правила нижнего регистра: `ДВАДЦАТЬ ДВА ФАЙЛА` превратится в
`22 ФАЙЛА`, а регистр остального текста сохранится.

Консервативное распознавание небольших ошибок в словах-числительных пока
является частью правила `numbers.ru-cardinals-to-digits`. Оно не исправляет
произвольные слова вне подтверждённой числовой фразы.

## Реестр и pipeline

Единый реестр находится в `src/transformation-rules.ts`. Он содержит стабильный
ID, версию поведения, пользовательские тексты, пример, значение по умолчанию и
функцию преобразования. Порядок записей в реестре является порядком pipeline.

При обработке запрос получает снимок включённых правил. Для каждого запущенного
правила результат содержит:

- стабильный `id`;
- `version` алгоритма;
- `changed` — изменило ли правило текст конкретного запроса.

Настройки, изменённые одновременно с уже начатой трансформацией, влияют только
на следующий запрос.

## Хранение

Пользовательские значения хранятся в SQLite-таблице `rule_settings`. Отсутствие
строки означает значение `defaultEnabled` из реестра. Благодаря этому новое
правило появляется без миграции настроек. Новые правила, способные заметно
менять текст, рекомендуется добавлять выключенными по умолчанию.

Таблица `transformations` содержит nullable-поле `rules_snapshot` с JSON-снимком
запущенных правил. Значения различаются намеренно:

- `NULL` — запись создана старой версией, данные о правилах неизвестны;
- пустой список — запись новая, но все правила были выключены;
- непустой список — правила выполнялись в указанном порядке.

В истории цветной badge означает, что правило изменило текст. Серый badge
означает, что правило было включено, но для этого текста ничего не изменило.

## HTTP API

Получение каталога и текущих значений:

```http
GET /api/rules
```

Изменение одного правила:

```http
PATCH /api/rules/case.lowercase
Content-Type: application/json

{"enabled":false}
```

Неизвестный ID возвращает `404`, а значение `enabled` не boolean — `400`.

`GET /api/transformations` дополнительно возвращает `appliedRules` для каждой
записи. Для старой истории это поле равно `null`.

## Добавление нового правила

1. Добавить стабильный ID и описание в `src/transformation-rules.ts`.
2. Реализовать чистую функцию `text -> text` без внешних побочных эффектов.
3. Выбрать позицию в реестре с учётом порядка преобразований.
4. Добавить отдельные и комбинированные тесты pipeline.
5. Увеличивать `version`, если меняется смысл существующего правила; ID при этом
   не менять.
6. Проверить пример и описание в обеих цветовых схемах UI.

Новая строка или колонка SQLite при этом не требуется. Отдельные параметры
правила стоит вводить только тогда, когда появится реальная пользовательская
потребность; до этого правило остаётся простым переключателем.
