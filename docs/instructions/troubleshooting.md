# Решённые проблемы разработки

Краткий справочник по уже встречавшимся проблемам сборки и разработки.

## `pymorphy3` не устанавливался в Debian VM

### Симптомы

- `python3` был доступен, но команд `pip`, `pip3` и модуля `venv` не было;
- загрузка Python-пакетов пыталась подключиться к
  `127.0.0.1:7890` и завершалась `Connection refused`;
- при этом в окружении также был настроен другой рабочий HTTP-прокси.

### Причина

Одновременно существовали переменные прокси в нижнем и верхнем регистре.
Нижнерегистровые `http_proxy` и `https_proxy` указывали на неработающий
локальный прокси и имели приоритет для `curl` и `pip`.

Проблема обнаружилась сравнением переменных:

```bash
env | rg -i '^(http|https)_proxy='
```

### Решение

Для диагностической установки не менялась система: конфликтующие переменные
удалялись только из окружения конкретной команды:

```bash
env -u http_proxy -u https_proxy curl https://pypi.org/
```

`get-pip.py`, `pip` и зависимости генератора были установлены во временный
каталог под `/tmp`, после чего пакеты подключались через `PYTHONPATH`. Это
позволило выполнить реальную проверку словоформ с `pymorphy3 2.0.6`, не меняя
системный Python и не добавляя Python в runtime сервера.

Для постоянного окружения разработки предпочтительнее установить поддержку
`venv`, создать `.venv` и поставить зависимости из
`requirements-generator.txt`. Обычная генерация словаря сторонних Python-
пакетов не требует.

## Проверка сообщала, что TypeScript-словарь устарел

После добавления новых форм команда с `--check --validate-morphology`
успешно проверила морфологию, но затем сообщила, что сгенерированный файл
устарел. Это две независимые проверки: исходные данные уже изменились, а
TypeScript-файл ещё не был перегенерирован.

Правильная последовательность:

```bash
npm run generate:numerals
npm run check:numerals
npm run validate:numerals-morphology
```

## Выделение текста CodeMirror оставалось прозрачным

### Симптомы

`Shift+Left`, двойной клик и мышь меняли диапазон выделения, но визуальной
подсветки не было ни в браузере, ни в Tauri WebView.

### Причина

Vite 8 преобразовал `light-dark(...)` в пару внутренних переменных Lightning
CSS. Их определения не попали в итоговый bundle, поэтому более специфичное
правило `.cm-selectionBackground` становилось недействительным во время
вычисления и давало прозрачный фон. Сам CodeMirror при этом корректно создавал
selection-layer и прямоугольник нужного размера.

### Решение

Для selection-layer используется обычный совместимый `rgba(...)` через
`background-color`, без `light-dark()` и theme-переменных. Тест production CSS
проверяет, что после минификации оба правила выделения сохранили валидный
`background-color`.

## Тесты Rust-лаунчера завершались с `cargo: not found`

`npm run test:launcher` не доходил до компиляции: в `PATH` среды запуска
отсутствовал `~/.local/bin`. Rust 1.98.0 уже был установлен, а находящиеся
в этом каталоге обёртки `cargo` и `rustc` задавали нестандартные
`CARGO_HOME` и `RUSTUP_HOME` в `~/.local/share/handy-processor-*`.

Достаточно добавить каталог в окружение команды из корня проекта:

```bash
PATH="$HOME/.local/bin:$PATH" npm run test:launcher
```

Все 9 тестов прошли. Переустановка Rust и изменение конфигурации оболочки
не потребовались.

## Проверка Windows-лаунчера из Linux останавливалась на `llvm-rc`

`cargo check --target x86_64-pc-windows-msvc` доходил до `tauri-winres`,
но build-script завершался с `NotAttempted("llvm-rc")`. Windows target Rust
был установлен; отсутствовал компилятор ресурсов EXE в `PATH`.

Для этой проверки Debian-пакет `llvm-19` был загружен и распакован через
`dpkg-deb -x` во временный каталог, без системной установки. Его
`usr/lib/llvm-19/bin` добавлен в `PATH` только команд проверки:

```bash
PATH="/tmp/handy-cross-tools.i2LUpf/extracted/usr/lib/llvm-19/bin:$HOME/.local/bin:$PATH" \
  cargo check --manifest-path launcher/src-tauri/Cargo.toml --target x86_64-pc-windows-msvc
```

После этого прошли `cargo check` и `cargo clippy -- -D warnings` для всего
Windows-лаунчера. Путь временный; после его очистки нужно снова подготовить
инструменты. Для полноценной линковки Windows EXE нужен Windows toolchain;
эта проверка его не заменяет.

## Двойное нажатие и безопасная вставка шаблонов

Обычная регистрация глобального сочетания не распознаёт двойные нажатия,
а наблюдение за Win без подавления открывает «Пуск» и меняет исходный фокус.
Добавлен Windows-hook на отдельном потоке и автомат двух нажатий с обязательным
отпусканием, проверкой времени, стороны клавиши и исходного окна. Одиночный
Win больше не запускает «Пуск» при включённой привязке; сочетания отменяют жест.

При проверке реализации обнаружена ещё одна тонкость: подавленный key-down
не обновляет `GetAsyncKeyState`. Поэтому проверка пропущенных отпусканий
теперь не сбрасывает перехваченные обычные клавиши — иначе автоповтор мог
выглядеть как новое нажатие, а двойной тап терялся.

Для вставки сохраняется внешняя цель до показа лаунчера. Перед Ctrl+V
проверяются окно/процесс, фокус, модификаторы и содержимое буфера. При отказе
нет слепого повтора; интерфейс сообщает причину. Ограничения и ручные проверки
описаны в [инструкции по шаблонам](../templates.md).

## Ревью шаблонов: запись клавиши вне окна и возврат старого файла

При записи хоткея закрытие окна в tray или переход в другое приложение не
отменяли ожидание клавиши. Следующий символ в чужом поле мог быть перехвачен
как новая привязка. Теперь React отменяет запись при `blur`/`pagehide` и
размонтировании, а Windows-hook дополнительно проверяет HWND окна записи
при старте, на таймере и перед обработкой каждого события клавиатуры.

При выборе нового файла переход на другую вкладку и обратно мог запустить
GET старого источника. Если его ответ приходил после успешного PUT нового
пути, интерфейс снова показывал старые строки, включая текст для копирования
и вставки. Выбор источника теперь блокирует параллельные перечитывания до
завершения операции; ранее начатые запросы по-прежнему отсеиваются по номеру.

Обе ошибки воспроизведены браузерными регрессионными тестами на коммите
`b946705`: запись не отменялась, а путь возвращался с `/test/new.txt` к
`/test/templates.txt`. С исправлениями оба сценария проходят.

## `Command ... not allowed by ACL` в WebView

Открытие «Шаблонов» завершалось `Command templates_desktop_state not allowed by
ACL`, а скачивание истории — аналогичным отказом для `save_history_export`.
В обычном браузере проблемы не было: там native-команды лаунчера не вызываются.

UI загружается из `http://127.0.0.1:<port>`. Для Tauri это remote origin,
несмотря на loopback-адрес. В Tauri 2.11.5 custom-команды из такого источника
проверяются ACL даже без application manifest. `core:default` разрешает
команды ядра Tauri, но не наши обработчики из `generate_handler!`.
Проверка URL внутри Rust-обработчика не помогает: ACL отклоняет вызов раньше.

Добавлены явные permissions `allow-history-export` и `allow-templates` в
`launcher/src-tauri/permissions/launcher.toml`; они подключены к существующей
capability для окна `main` и `http://127.0.0.1:*/*`. Сам обработчик дополнительно
проверяет точный origin с настроенным портом. Файл permissions включён и в ZIP
исходников. Это соответствует [модели разрешений Tauri](https://v2.tauri.app/security/permissions/).

Ошибки команд шаблонов записываются через HTTP в `handy-processor.log` с
`event: "templates"`, именем команды и сведениями о WebView. Аргументы native-
вызова (текст шаблона, буфер) не добавляются. Если запись удалась, интерфейс
показывает путь к логу; если нет — сохраняет исходную ошибку. Экспорт истории
продолжает использовать `event: "history-export"`.

Проверка `npm --prefix launcher run test:acl` использует настоящий ACL resolver
Tauri и build-generated manifests: разрешает команды из loopback-окна `main`
и проверяет отказ для других окон, сторонних адресов и незаявленных команд.
Для неё нужны desktop build-зависимости. Браузерные тесты отдельно проверяют
запись обоих отказов ACL и отображение пути к логу.

После обновления исходников нужно **пересобрать и заменить лаунчер EXE**, а
также server EXE с новым UI/API (`npm run build:windows:portable`). Простое
обновление страницы или замена только серверного EXE не изменяет встроенную
ACL старого `HandyProcessor.exe`.

## Резервная версия шаблонов терялась при параллельном чтении

Запоздалый GET мог заменить последнюю корректную версию данными старого
источника уже после выбора нового файла. При следующей ошибке чтения нового
файла список становился пустым вместо показа резервной версии. Аналогично
два чтения одного файла могли сохранить устаревшее содержимое поверх свежего.

Теперь успешные чтения и выбор источника имеют номера версий; старый запрос
не заменяет более свежую резервную копию. Регрессионные тесты задерживают
чтение, выполняют смену источника или обновление файла, затем проверяют
сохранность актуальных шаблонов при повреждении файла.

## Настройки хоткея сбрасывались запоздалым ответом лаунчера

При повторном открытии «Шаблонов» интерфейс запрашивает состояние лаунчера.
Если до прихода ответа изменить интервал или сохранить настройки, старый
ответ мог вернуть прежнее значение в поле и сводке хоткея. Последующее
нажатие «Сохранить» отправляло бы это устаревшее значение обратно в лаунчер.

Теперь ответы состояния учитывают версии редактирования и сохранения.
Изменённый пользователем черновик не сбрасывается, а ответы, пересекающиеся
с сохранением, игнорируются. Повторный вызов сохранения во время текущего
также блокируется. Браузерный тест задерживает native-ответ и проверяет
сохранность как несохранённого интервала, так и уже сохранённых настроек.

## «Вставить сразу» заменяла содержимое буфера

Раньше команда записывала текст в clipboard до проверки цели вставки и
оставляла его там даже при отказе. Теперь Windows-лаунчер сначала проверяет
цель, сохраняет все доступные форматы буфера, временно публикует текст и
после Ctrl+V с паузой 500 мс восстанавливает снимок. Снимок восстанавливается
и при ошибке скрытия окна/возврата фокуса/отправки клавиш. Команда копирования
по-прежнему намеренно заменяет буфер.

Форматы копируются независимыми Windows-handles с учётом
[правил владения памятью буфера](https://learn.microsoft.com/en-us/windows/win32/dataxchg/clipboard-operations).
Перед восстановлением под блокировкой буфера проверяется
[номер последовательности](https://learn.microsoft.com/en-us/windows/win32/dataxchg/using-the-clipboard):
если пользователь или другая программа уже сделали новую копию, она остаётся.
Номер запоминается после закрытия и повторного открытия буфера: Windows может
добавить автоматически преобразованные текстовые форматы при закрытии.
Уникальная метка операции проверяет, что в этом промежутке буфер не заменён.
Неподдерживаемый формат отменяет вставку до изменения буфера. Ошибки native-
команды проходят через существующее логирование `event: "templates"`.

Кнопки строки теперь используют включённые уровни с разделителем ` > `.
Готовая фраза вставляется отдельной иконкой целиком, включая пробелы/дефисы;
нажатие на текст фразы добавляет её в фильтр, где пробелы и дефисы разделяют
обязательные префиксы. Инструкция и ручной Windows-тест — в
[документации шаблонов](../templates.md).

Для применения нужно пересобрать сервер с UI и Windows-лаунчер
(`npm run build:windows:portable`); замены только одного EXE недостаточно.

## После вставки следующая буква могла сработать как Ctrl-сочетание

Вставка отправляла Ctrl-down, V-down и V-up одним пакетом, ждала 100 мс
и лишь затем отпускала Ctrl. При быстром продолжении ввода, например буквой
`a`, целевое приложение могло получить Ctrl+A вместо обычного символа.

Теперь все четыре события, включая Ctrl-up, отправляются одним вызовом
[SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput).
Пауза 500 мс перед восстановлением буфера остаётся после отпускания клавиш.
При частичном отказе отпускаются только клавиши, нажатия которых были приняты;
при полном отказе лишних key-up нет. Повторной отправки Ctrl+V не происходит.

Добавлены тесты с моделью состояния клавиатуры: успешный пакет не оставляет
Ctrl нажатым между вызовами; каждый вариант частичного/полного отказа не
повторяет вставку; отказ отпускания клавиш возвращает отдельную ошибку.
Для применения исправления нужно пересобрать Windows-лаунчер.
