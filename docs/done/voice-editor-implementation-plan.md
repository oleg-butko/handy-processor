# Голосовой редактор: архитектура и план реализации

Статус: выполнено 24 августа 2026 года. Реализация завершена последовательными
коммитами от `6060c63` до `d337337`, включая финальное ревью гонок сессии и
сохранности undo-истории.

## Цель

Добавить в Web UI простой текстовый редактор для частого голосового ввода и
ручных исправлений. В отличие от внешней вставки, правила редактора должны
учитывать контекст всего документа и положение курсора.

Первое контекстное поведение:

- в середине предложения распознанный фрагмент переводится в нижний регистр;
- в начале предложения регистр фрагмента сохраняется;
- решение и использованный контекст видны в истории.

Пользовательское название функции и вкладки — **Голосовой редактор**. Во
внутренних контрактах используются термины `voice-editor` и
`TransformationContext`.

## Ограничение интеграции с Handy

Текущий OpenAI-compatible запрос Handy содержит распознанный фрагмент, но не
содержит текст целевого поля, позицию курсора или идентификатор приложения.
Поэтому контекст поддерживает браузерный редактор:

```text
Редактор в браузере
  ├─ текст документа
  ├─ выделение и курсор
  └─ признак активности
          │
          v
EditorSessionRegistry в Node
          │
Handy ───► POST /v1/chat/completions
          │
          ├─ редактор активен → source: voice-editor + контекст
          └─ иначе           → source: external
                              │
                              v
                    контекстный pipeline
```

В первой версии сервер по-прежнему возвращает преобразованный фрагмент Handy,
а Handy вставляет его обычным способом. Это сохраняет существующий надёжный
механизм вставки и делает одну диктовку одной undo-операцией редактора.

Сервер не может абсолютно точно определить целевое приложение только по
запросу Handy. Редактор поэтому должен показывать явный индикатор активности,
использовать ограниченный срок жизни контекста и безопасно переходить к
`external`, если контекст отсутствует, неоднозначен или устарел. Поведение
фокуса и overlay Handy необходимо отдельно проверить на Windows.

## Модель контекста

Pipeline должен принимать расширяемый объект вместо отдельных флагов:

```ts
interface TransformationContext {
  source: "external" | "voice-editor";
  editor?: {
    sessionId: string;
    documentRevision: number;
    selectionStart: number;
    selectionEnd: number;
    sentencePosition: "start" | "middle" | "unknown";
  };
}
```

Полный текст документа используется для вычисления контекста, но не
дублируется в каждой записи истории. История хранит только факты, которые
участвовали в принятии решений правилами.

### Начало предложения

Для первой версии позиция считается началом предложения:

- в начале документа;
- после `.`, `!`, `?` или `…`, с разрешёнными пробелами и закрывающими
  кавычками или скобками.

В остальных корректных позициях это середина предложения. При замене
выделения проверяется его начало. Некорректная или устаревшая позиция даёт
`unknown`; контекстное правило в таком случае пропускается.

## Контекстные правила

Текущее правило — чистая функция `text -> text`. Расширенная модель должна
отдельно фиксировать условие и результат его оценки:

```ts
type RuleOutcome = "changed" | "unchanged" | "skipped";

interface RuleEvaluation {
  id: string;
  version: number;
  outcome: RuleOutcome;
  reason?: string;
}
```

Это различает три ситуации: правило изменило текст, было выполнено без
изменений или было пропущено из-за контекста. Отключённые пользователем правила
в снимок по-прежнему не попадают.

Первое специальное правило:

| Поле | Значение |
| --- | --- |
| ID | `editor.case.lowercase-inside-sentence` |
| Название | Нижний регистр внутри предложения |
| Область | только `voice-editor` |
| Условие | `sentencePosition == middle` |
| Действие | перевести вставляемый фрагмент в нижний регистр |

Существующее `case.lowercase` сохраняет поведение внешнего post-processing.
Правила числительных и пунктуации могут работать для обоих источников. Реестр
должен показывать область применения и отдельную группу правил голосового
редактора.

## Сессия редактора

Страница создаёт случайный `sessionId` и синхронизирует с сервером:

- текущий текст;
- начало и конец выделения;
- монотонную ревизию документа;
- активность редактора;
- время последнего обновления.

Состояние активной сессии хранится в памяти процесса. Защита от ошибочной
классификации включает ограниченный срок жизни, проверку диапазона выделения и
ревизии, защищающие от поздних обновлений. Новая активная сессия деактивирует
предыдущую; при отсутствующем или устаревшем контексте запрос считается
внешним.

## История и SQLite

Следующая миграция добавляет:

```sql
ALTER TABLE transformations
  ADD COLUMN source TEXT NOT NULL DEFAULT 'external';

ALTER TABLE transformations
  ADD COLUMN context_snapshot TEXT;
```

`source` является отдельной колонкой для отображения и будущей фильтрации.
`context_snapshot` остаётся версионированным JSON, чтобы новые признаки
контекста не требовали миграции схемы. Снимок правил получает новую версию с
`outcome` и необязательным стабильным `reason`.

История показывает:

- «Внешний ввод» или «Голосовой редактор»;
- начало, середину предложения либо неизвестный контекст;
- правила, изменившие текст, не потребовавшие изменения или пропущенные по
  условию.

Старые записи продолжают читаться: отсутствие новых колонок мигрируется как
`external`, а старый `changed` преобразуется в соответствующий `outcome`.

## UI редактора

Для поля используется CodeMirror 6 в режиме обычного текста с оболочкой
Mantine. Он предоставляет устойчивую историю изменений, точное выделение и
программные команды без самостоятельной реализации сложной логики undo.

Первая версия содержит:

- вкладку «Голосовой редактор»;
- большое поле с переносом строк;
- кнопки Undo и Redo;
- сочетания Ctrl+Z, Ctrl+Y и Ctrl+Shift+Z;
- индикатор готовности к голосовому вводу;
- автосохранение одного черновика в SQLite;
- копирование всего текста;
- счётчик слов и символов.

Для исходного этапа undo-историю между перезапусками сохранять не требовалось.
В последующем расширении появились именованные заметки: теперь снимок
CodeMirror с undo/redo сохраняется в SQLite и восстанавливается вместе с
текстом, не создавая дополнительную операцию в истории.

## Этапы и коммиты

1. `docs: plan voice editor implementation`
   Зафиксировать архитектуру, ограничения и порядок работ.
2. `refactor(rules): add transformation context`
   Добавить контекст, результаты оценки и тесты определения позиции без
   изменения внешнего поведения.
3. `feat(history): store transformation context`
   Добавить миграцию, источник, JSON-контекст и обратную совместимость.
4. `feat(editor): track active editor sessions`
   Реализовать сессии, ревизии, выделение, срок жизни и HTTP API.
5. `feat(rules): add contextual editor casing`
   Добавить специальное правило и области применения.
6. `feat(ui): add voice editor`
   Добавить CodeMirror, undo/redo, индикатор, синхронизацию и автосохранение.
7. `feat(history): show editor context`
   Показать источник, позицию и причины пропуска правил.
8. `docs: document voice editor usage`
   Описать пользовательский сценарий, API и известные ограничения.
9. Выполнить полное ревью, тесты и отдельными коммитами исправить найденные
   важные дефекты. Исправлены сохранение undo-истории между вкладками и гонки
   поздних обновлений активности.

## Будущее расширение

Ответ Handy может заменить только вставляемый фрагмент. Правила, которым нужно
изменять уже существующий окружающий текст, потребуют канала событий между
сервером и редактором и структурированных изменений документа.

Handy уже не выполняет вставку, если итоговый текст пуст. Поэтому в будущем
сервер сможет передать изменение напрямую редактору, дождаться подтверждения и
вернуть Handy пустую строку. Такой протокол требует обработки таймаутов и
защиты от двойной вставки и намеренно не входит в первую версию.
