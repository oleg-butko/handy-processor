# Коррекция в Handy Processor

Во вкладке **Список правил** появился пункт **Коррекция терминов и фраз**
(`recognition.terms-and-phrases`). По умолчанию выключен. Переключатель сохраняется
в общей БД настроек и действует на следующие запросы как внешнего ввода, так
и голосового редактора. Отключение остальных правил не мешает коррекции.

Объединены ручные варианты, словоформы, фразы, произношения русских аббревиатур,
контекстные ограничения и веса. Их кандидаты конкурируют в одном TermEngine
на исходном тексте; исправления не запускают друг друга повторно. Это зависимые
части одного метода. Общая словарная B2-коррекция и взвешенная дистанция по
умолчанию не добавлены: обзор не подтвердил их устойчивый выигрыш. Полный
словарь здесь используется для проверки существующих слов, а не для выбора
самого частотного слова вместо термина.

Коррекция выполняется перед форматированием регистра, числительных и точки.
Например, `КАЛИБОРД` защищён от коррекции; последующее правило нижнего регистра
может превратить его в `калиборд`, но повторной коррекции уже не будет.
Порядок форматирования и коррекции не объявляется взаимозаменяемым.

## Запуск и настройки

Из корня проекта:

```bash
npm run build
npm start
```

`npm run dev` также собирает worker. Нужен Rust/Cargo с уже доступными
зависимостями `rechprav/Cargo.lock`: сборка использует `--locked --offline`.
Если Cargo отсутствует в PATH, проверяется `~/.local/bin/cargo`; путь можно
задать переменной `CARGO`. Это не установка Rust и не загрузка зависимостей.

В текущей VM полный словарь уже подготовлен в
`rechprav/artifacts/opencorpora-wordfreq/dictionary.rpt`. В Git этот большой
генерируемый файл не хранится. На другой машине его нужно подготовить по
[описанию ресурсов](resource-sources.md) и [формату индекса](packed-index.md).
Отсутствие словаря или binary показывается как пропуск коррекции, остальные
правила продолжают работать.

Редактируемый стартовый профиль: [handy-terms.toml](../../rechprav/handy-terms.toml).
Он содержит примеры пользователя, небольшой набор фраз и контекстные варианты
терминов. Для параметров действует существующий [формат](terms.md):

- `enabled` у набора/термина выключает соответствующий каталог;
- `boost` меняет предпочтение цели; это не вероятность;
- `aliases` перечисляет варианты; `forms` — формы слова;
- `context_patterns`, `require_context`, `context_exclusions` задают условия;
- `generation = "exact"` ограничивает запись её точными вариантами;
- `pronunciation = "ru_letters"` дополняет ручные варианты названиями букв.

После правки файла откройте в карточке правила **Словарь терминов и настройки**
и нажмите **Загрузить профиль заново**. Там показан фактический путь к профилю.
Само изменение файла не переключает уже загруженный engine. Во время обработки
запросов перезагрузка отклоняется: нужно дождаться их завершения. Перезагрузка
загружает новый процесс, сохраняя прежний рабочий профиль. При ошибке файла или
таймауте загрузки прежний профиль продолжает работать, а карточка показывает
ошибку обновления. Запросы, поступившие во время загрузки, заканчиваются на своём
поколении; оно освобождается после последнего запроса. Следующая перезагрузка
отклоняется, пока ещё загружается кандидат или завершаются запросы прежнего
поколения. Поэтому на время обновления в памяти могут находиться два словаря.
Это ручной TOML-профиль,
не механизм публикации подтверждённых learned rules из опытов 014–020.

Для другого расположения задать при запуске сервера:

```bash
HANDY_PROCESSOR_CORRECTION_BINARY=/path/to/correction_worker \
HANDY_PROCESSOR_CORRECTION_CONFIG=/path/to/terms.toml npm start
```

Без переменных используются пути относительно runtime directory:
`rechprav/target/release/examples/correction_worker` (`.exe` в Windows) и
`rechprav/handy-terms.toml`. Для отдельно собранного SEA-сервера нужно доставить
worker, профиль и словарь в это расположение либо указать переменные выше.
Windows portable-сборка включает эти файлы автоматически, как описано ниже.

## Windows portable и ошибка ENOENT

`spawn ...\correction_worker.exe ENOENT` означает, что сервер не смог найти
исполняемый файл корректора по указанному пути. Кнопка **Загрузить профиль
заново** запускает уже собранный worker; она не собирает и не скачивает его.
До исправления этапа 024 команда `npm run build:windows:portable` собирала
только сервер и лаунчер. Теперь она также вызывает `npm run build:correction`
и включает runtime коррекции в результат.

На Windows из корня обновлённых исходников:

```powershell
# Однократно на машине с Rust/Cargo: заполнить кеш зависимостей worker.
cargo fetch --manifest-path rechprav/Cargo.toml --locked
npm run build:windows:portable
```

Нужен нативный Windows Rust toolchain с поддержкой edition 2024 и установленными
MSVC Build Tools, как для лаунчера. Основная сборка worker остаётся `--locked
--offline`. Собранный в Debian ELF-файл нельзя переименовать в `.exe` для Windows.

Полный `dictionary.rpt` не хранится в Git. При переносе через `npm run
archive:sources` новый ZIP уже содержит подготовленный в VM словарь, исходники
`rechprav`, Cargo.lock и профили. Если получаете проект через Git, отдельно
скопируйте `rechprav/artifacts/opencorpora-wordfreq/dictionary.rpt` из VM с
сохранением пути либо подготовьте его по инструкциям выше. Частотный индекс,
Python-окружение и экспериментальные корпуса для работы правила не нужны.

Готовый каталог должен содержать:

```text
release/handy-processor-windows-x64/
  HandyProcessor.exe
  handy-processor-server.exe
  config.json
  rechprav/
    handy-terms.toml
    handy-dictionary.toml
    DICTIONARY-NOTICE.md
    target/release/examples/correction_worker.exe
    artifacts/opencorpora-wordfreq/dictionary.rpt
```

При повторной упаковке существующие `rechprav/handy-terms.toml` и
`rechprav/handy-dictionary.toml` в готовом каталоге сохраняются: пользовательские
термины и настройки словаря не сбрасываются. Binary и стандартный словарь
обновляются. Дополнительные ресурсы пользовательского профиля нужно доставлять
самостоятельно. Упаковщик проверяет наличие обязательных файлов и Windows-формат
worker до изменения готового каталога.

Для исправления существующей сборки без повторной сборки сервера/лаунчера:

```powershell
npm run build:correction
npm run package:windows:portable
```

Это требует уже имеющихся `sea-build/handy-processor.exe`, `sea-build/config.json`
и `launcher/src-tauri/target/release/HandyProcessor.exe`, а также словаря выше.
После обновления файлов запустите приложение и нажмите **Загрузить профиль
заново**. Для отдельной проверки переносимого runtime из исходников доступна
команда `node rechprav/scripts/check_runtime_bundle.mjs`: она копирует комплект
во временный каталог, запускает настоящий worker и проверяет четыре примера.

## Объяснения в истории

У записи раскрывается **Почему выбраны эти исправления**. Для каждого фрагмента
видно выбранное слово либо сохранение исходника. Таблица содержит конкурентов,
alias, расстояние, набор, итоговый балл и причину допуска/отказа. Внутри строки
раскрывается состав оценки: базовые 4 балла, общий вес, вес набора и термина,
штраф расстояния, бонус контекста, штраф известного слова и поправка исходника.
Показаны сработавшие контексты/исключения и пороги решения. Даже высокий балл
не отменяет контекстный запрет или конфликт пересекающихся фрагментов.

Это сохранённый снимок, а не новый запуск алгоритма. Старые записи без
диагностики продолжают открываться. Схема SQLite не меняется: дополнительные
поля находятся в существующем `rules_snapshot`. История обновляется при
переходе на вкладку, также остаётся кнопка обновления.

Диагностика ограничена 32 фрагментами и 6 кандидатами на фрагмент. Выбранные
фрагменты выводятся первыми; число пропущенных элементов показано явно.
Ограничение диагностики не меняет выбор исправлений.

## Ограничения процесса

Worker загружается при первом включённом запросе и остаётся в памяти. Node
общается с ним асинхронно через JSONL. Ограничения: 16 КиБ UTF-8 на текст,
64 КиБ сериализованная строка запроса, 8 ожидающих запросов, 30 секунд на запуск,
5 секунд на анализ, 2 МиБ буфера ответа. По таймауту процесс завершается,
ожидающие запросы получают явный пропуск; следующий запрос может запустить
новый процесс. Лимит очереди общий для поколений. Текст ответа проверяется
отдельно от коротких полей диагностики: допустимые многократные расширения
aliases не отклоняются только за превышение 32768 символов. Сохраняются
ограничения в 1 Ми символов результата и 2 МиБ транспортного буфера.
При остановке сервера сначала отменяется работа worker, затем завершаются
HTTP-ответы и закрывается БД; зависшая загрузка не удерживает остановку сервера.

При неполном поиске, ошибке запуска, переполнении очереди или неверном ответе
исходник сохраняется для последующих правил. Причина остаётся в истории.
Это не обещание безошибочной коррекции: буквальные упоминания вроде
«слово этабы содержит ошибку» пока могут ошибочно исправляться.

Проверки: настоящий Rust worker, HTTP переключатель и SQLite после повторного
открытия, конфликты/веса/контекст/границы, ошибки/таймаут/очередь и браузерный
сценарий с раскрытием оценок. Результаты технических примеров хранятся
в `rechprav/experiments/021-rule-integration*`.
