# 018: атомарная публикация (протокол до реализации)

Дата: 2026-09-22. Предыдущий результат: 017-profile-composition-v3.
Проверяем жизненный цикл профиля, а не новую гипотезу качества ASR.

## Контракт

Отдельная экспериментальная SQLite-база с собственным application_id/schema,
один scope на базу. Нативный Node SQLite уже доступен в проекте; новые зависимости
не нужны. Снимок содержит точные UTF-8 тексты composition manifest/report/TOML,
manual config, bindings, events и decisions. Rust заново проверяет hashes,
скомпилированные источники, ресурсы, registry/composition и создание TermEngine.
Недостаточно проверить только JSON или совпадение двух самостоятельно изменённых hashes.

Два шага: request регистрирует намерение с expected_revision, затем publish
валидирует сохранённые байты вне транзакции и активирует их, только если request
по-прежнему последний. Это позволяет отменить устаревшую сборку ещё до завершения
новой. Новый невалидный запрос оставляет прежний активный профиль. Автоматического
rebase/retry с новым expected_revision нет. Повтор одного request_id с тем же
payload идемпотентен; другой payload запрещён. Повтор успешной публикации возвращает
старый receipt, не переключая активный профиль обратно.

Снимок, активное поколение и receipt фиксируются одной BEGIN IMMEDIATE/COMMIT
транзакцией (DELETE journal, synchronous FULL). Читатель получает целый снимок
одной read transaction. Никаких промежуточных TOML или указателя на неполный
каталог. SQLite выбран вместо самодельного lock + rename + directory fsync:
он уже решает транзакционность и восстановление журнала для этого прототипа.

## Зафиксированные проверки

1. Первая публикация; воспроизводимое содержимое профиля 017.
2. Повтор request/publish; конфликт id; старый receipt после новой публикации.
3. CAS двух процессов на одном revision: ровно один новый запрос.
4. Старое намерение, новая заявка, завершение старой сборки: отказ.
5. Новая заявка во время Rust validation: commit старой запрещён.
6. SIGKILL после INSERT, перед COMMIT и после COMMIT; reopen/integrity_check;
   активен целиком старый либо целиком новый профиль, повтор после lost receipt.
7. Чтение во время незавершённой записи: прежний целый снимок.
8. Отсутствующий/изменённый файл, неправильный hash, валидный TOML с подменённым
   правилом и пересчитанными output hashes, изменённые ресурсы/исходники/scope:
   отказ, прежнее поколение сохранено.
9. Чужая SQLite, неизвестная schema, invalid UTF-8, лимиты: отказ.
10. Выключенный профиль также публикуется; качество коррекции не перенастраивается.

Не подключаем рабочий сервер/UI. SIGKILL не моделирует отказ диска/питания.
Внешние словари пока не копируются в SQLite: хеши закреплены и проверяются при
валидации, но для будущего reader нужны повторная проверка и удержание загруженного
engine. Snapshot API пока транспорт, не hot reload. Локальная база и compiler
считаются доверенными; hashes не являются подписью или разрешением пользователя.
