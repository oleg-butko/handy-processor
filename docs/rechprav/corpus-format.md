# Корпус Rechprav: схема 1

Текущий пользовательский выбор: пока использовать технические примеры.
В `rechprav/data/fixtures/corpus.jsonl` находятся 12 искусственных записей
с заранее заданными эталонами. `reviewed` в этих fixtures означает проверенную
согласованность технического примера; это не ручная расшифровка реального аудио.

## Подготовка

`prepare` принимает UTF-8 файл «одна физическая строка — один фрагмент», создаёт
JSONL с `gold: null`, `edits: []`, `annotation_status: pending`, `split: unassigned`.
Аргументы `--group` и `--kind synthetic|real-asr` обязательны. Пустые строки
сохраняются; завершающий перевод строки не добавляет фантомную запись.
LF/CRLF/CR отделяют записи; окончания строк не входят в их source. Для точного
сохранения всего файла используйте `review`, который хранит endings отдельно.

Старый экспорт Handy с `--- РЕЗУЛЬТАТ ---` и `==============================` отклоняется.
Из него нельзя автоматически узнать gold; кроме того, разделители могут встретиться
в самих записях. Отдельный [инструмент разметки](../../rechprav/annotator/README.md)
уже импортирует структурированную историю, но его проект ещё нужно преобразовать
в корпус этой схемы. Валидатор уже принимает многострочный source
в одной JSONL-записи: внутренние переводы строк записываются как JSON escapes.
Новый JSONL-экспорт истории Handy хранит исходник, результат и диагностику,
но не является размеченным корпусом этой схемы: результат процессора нельзя
автоматически считать проверенным `gold`.

## Запись

```json
{
  "schema_version": 1,
  "id": "pilot:000001",
  "group_id": "session-001",
  "split": "unassigned",
  "source": "драйвир",
  "gold": "драйвер",
  "edits": [
    {
      "byte_start": 0,
      "byte_end": 14,
      "token_start": 0,
      "token_end": 1,
      "replacement": "драйвер"
    }
  ],
  "tags": ["oov"],
  "provenance": {
    "kind": "synthetic",
    "origin": "authored example",
    "asr_model": null
  },
  "annotation_status": "reviewed"
}
```

В файле каждый объект находится на одной физической строке. Неизвестные поля
отклоняются, чтобы опечатки в названиях не игнорировались. `id` уникален во всех
переданных файлах. `group_id` объединяет одну сессию или близкие повторения.
`provenance.origin` описывает источник; `asr_model` можно оставить null, если неизвестна.

`split`: `unassigned`, `train`, `dev`, `test`. Валидатор считает непомеченные записи,
но не выполняет случайное разбиение. Разбивать реальные данные нужно по группам
после удаления пересечений. Данные fixtures целиком имеют split `dev`; это не
обучающая/тестовая выборка для измерения качества.

## Как разметить фрагмент

1. Сохранить `source` без изменений. Написать `gold`, исправив только известные
   ошибки распознавания. Правильный фрагмент: `gold == source`, `edits: []`.
2. Через `inspect 'исходный текст'` получить lexical indices и UTF-8 byte ranges.
   Диапазоны нулевые и полуоткрытые. Русская буква обычно занимает два байта:
   это не номера символов и не UTF-16 offsets браузера.
3. Заполнить отсортированные непересекающиеся `edits`. Byte range начинается
   на первом lexical token диапазона и заканчивается на последнем. Применение
   всех правок обязано точно воспроизвести gold, включая пробелы вне правок.
4. Поставить `reviewed`. При неоднозначности оставить `gold: null`, `edits: []`
   и поставить `ambiguous`, не угадывая сказанное без аудио.
5. Запустить `validate` со всеми split-файлами одновременно. Проверка одного файла
   не обнаружит совпадение с непереданным файлом.

Схема поддерживает замены целых lexical spans, включая 2→1 и 1→2. Вставки в
пустой диапазон, удаления без замены и изменения пунктуации в этой версии
отклоняются. Если такой реальный случай появится, расширить схему/метрики
отдельно; не подгонять gold под возможности валидатора. Правка не пересекает
перевод строки. Source, состоящий только из знаков препинания, допустим без правок.

`pending` и `ambiguous` не могут содержать gold/edits. Benchmark отказывается
от pending; ambiguous исключает из оценки и явно считает. Без reviewed он
завершается ошибкой. В одном benchmark не смешиваются reviewed записи разных
splits или provenance kinds.

## Метрики этой версии

KEEP возвращает исходный текст. Для 1→1 считаются TP/FP/FN и правильные входные
позиции; в текущем корпусе 6 ошибок 1→1. Неисправленные compound spans показываются
отдельно, но входят в полный WER. Позиции внутри таких spans исключены из
знаменателя правильных слов; невозможность их исправить не скрывается.
Evaluator теперь принимает KEEP или baseline, выдающий замены 1→1 по исходным
диапазонам. Он сравнивает их с gold-разметкой, считает TP/FP/FN и отдельно вред
правильным позициям. Предсказания, меняющие число lexical tokens, пока отклоняются;
произвольный внешний текст без исходных диапазонов не является его входом.

В `metrics.json` schema 2 `overall_precision` учитывает все предложенные правки,
включая неправильные предложения внутри неподдерживаемых gold compounds.
`all_gold_span_recall` делит число точно исправленных gold spans на общее число
размеченных spans. Это заменяет старое KEEP-only поле `all_error_recall`:
нельзя делить число исправленных spans на число WER-операций и называть результат
общим recall. WER и число его S/D/I сохраняются отдельно. `rates_1_to_1` обозначает
явно ограниченный срез, не заменяет общую precision.

Shortlist recall@K считает совпадение нормализованного gold с выданными кандидатами
после политики защиты/OOV. Его знаменатель — все gold ошибки 1→1, в том числе
защищённые или уже словарные. Это end-to-end доступность кандидата, не измерение
полноты чистого поиска. Последняя отдельно проверена против полного перебора
на маленьком исчерпывающем наборе в тестах.

WER сравнивает lexical sequences с NFC, нижним регистром и выбранным режимом е/ё.
Алгоритм учитывает вставки/удаления/замены, не использует zip. При одинаковой
стоимости предпочитает диагональ, затем удаление, затем вставку.
Correction counts используют точные исходные и эталонные замены, поэтому
случаи изменения только регистра/е/ё могут давать разницу с нормализованным WER.
Нулевой знаменатель всегда даёт null, в том числе WER корпуса без gold tokens.

Проверка leakage сравнивает группы и нормализованные последовательности lexical
tokens, включая пересечения source одного примера с gold другого. Семантические
перефразы автоматически не обнаруживаются: их нужно объединять через `group_id`.

Приватные материалы хранить в `rechprav/data/private/`, подробные результаты —
в `rechprav/experiments/private/`; эти каталоги исключены из Git.
