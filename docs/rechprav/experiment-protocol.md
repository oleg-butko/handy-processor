# Протокол экспериментов Rechprav

Статус: спецификация для реализации benchmark. Метрики качества ещё не измерены.

## Данные и защита от утечки между разбиениями

JSONL хранит запись целиком, включая многострочный source. Обязательны `id`,
`group_id`, `source`, `gold`, `edits`, `tags`, `provenance`, `annotation_status`;
по возможности — ASR engine/model/version, session id и дата. Byte ranges и
lexical indices имеют версионированную схему; индексы токенов нулевые,
диапазоны полуоткрытые. Дата и модель могут быть unknown, но не выдумываются.

Gold меняет только доказуемые ошибки распознавания, не переписывает стиль,
пунктуацию или числительные в цифры. Вводить `ambiguous` для фрагментов, где без
аудио нельзя восстановить сказанное; хранить их вне основного quality-score,
но обязательно отчитываться об их числе. Примеры из задания — fixtures,
пока не подтверждено их происхождение из реального ASR.

Train служит обучению confusion/LM, dev — выбору параметров, test — финальной
проверке. Дубликаты, близкие перефразы одной записи и одна сессия принадлежат
одному разбиению. Проверять пересечения нормализованных исходников/эталонов
и групп. Seed, split-manifest и хеш корпуса фиксируются до настройки.
Частоты/domain aliases, полученные из данных, строятся только по train;
пользовательский словарь фиксируется до dev/test и имеет отдельный provenance.

Два набора: естественная история с исходной долей ошибок и challenge-набор
редких/опасных случаев. Их показатели не смешиваются. Синтетика — отдельный
stress-test. Не отбирать только ошибочные строки: иначе precision и FCR
не описывают реальное использование. Корпус увеличивается по числу правильных
слов и предложенных замен, а не только по числу строк.

Личные исходники и построчные результаты хранятся локально вне отслеживаемых
путей (`rechprav/data/private/`, `rechprav/experiments/private/`). В Git —
безличные fixtures, конфиги, агрегаты и разрешённые примеры. Новую версию
корпуса создавать отдельно, чтобы не переписывать использованные результаты.

## Определения метрик

Сначала реализовать случай 1→1 с явно размеченным выравниванием. Для каждой
позиции source/gold/prediction:

| Обозначение | Значение |
|---|---|
| TP | source ≠ gold и prediction = gold: исправлена настоящая ошибка |
| FP | prediction ≠ source и prediction ≠ gold: неверная предлагаемая правка |
| FN | source ≠ gold и prediction ≠ gold: исходная ошибка осталась |
| C | число правильных входных позиций source = gold |
| H | source = gold и prediction ≠ gold: испорчены правильные позиции |
| E | число исходных ошибок 1→1 в оцениваемом подмножестве |

Неверная замена ошибочного слова одновременно даёт FP и FN. H — часть FP,
но не все FP. KEEP на ошибке даёт FN, на правильном слове не даёт FP.

- Precision = TP / (TP + FP).
- Recall для 1→1 = TP / E; дополнительно отчёт по всем lexical errors.
- FCR = H / C. Также H на 1000 правильных слов и доля строк хотя бы с одной H.
- Fβ = (1+β²)TP / ((1+β²)TP + β²FN + FP), β=0.5 и β=1.
- WER = (S+D+I)/N_gold до/после на полной последовательности lexical tokens;
  пунктуация исключена. Нормализация регистра/е/ё зафиксирована; отдельно exact
  результаты и protected-token violations. Строки с пустым gold учитывать через
  суммарные I в corpus WER, не делить их по отдельности на ноль.
- Recall@K кандидатов: доля эталонных замен в K выданных кандидатах среди ошибок
  1→1; отдельно среди покрытых словарём. KEEP исключён из списка кандидатов.
  Считать до decision policy, указывать правило предварительной сортировки.
- Coverage: доля входных lexical positions с предложенной заменой; отдельно
  доля ошибок, для которых в принципе есть словарный кандидат.

При нулевом знаменателе значение null/N/A, не 100%. Для KEEP precision=N/A,
recall=0 при E>0, FCR=0 при C>0. F-score=0 при наличии ошибок и отсутствии TP.
Пустой корпус не является успешным benchmark. Числители и знаменатели сохраняются
рядом с долями, чтобы одинаковые проценты с разным объёмом не выглядели равноценными.

Для вставок, удалений и 2→1/1→2 нужен отдельный детерминированный span alignment
с проверенными примерами; не применять покомпонентный zip. Неподдерживаемые случаи
участвуют в полном WER/общем recall и перечисляются отдельно от 1→1 precision.
Правило совпадения правок: совпадают исходный диапазон и эталонная замена.

Срезы: OOV/real-word, обычные/редкие/доменные слова, имена, латиница, числа/пути,
длина ≤3/4–8/>8, типы фонетических ошибок, word boundary, правильные строки.

## Уверенность и выбор порогов

Сначала score и margin — эвристики. Не подписывать их как P(correct).
Сохранять score лучшего кандидата, KEEP и второго варианта, причины отказа,
полный feature vector. Все пороги подбирать только на dev; заранее задавать
ограниченный список конфигураций и сохранять все прогоны, включая неудачные.

Начальные цели автокоррекции: precision ≥99%, FCR ≤0.1%. Отчёт включает
односторонние 95% биномиальные границы и парные сравнения алгоритмов с bootstrap
по сессиям, сохраняющим зависимость слов одной записи. При слишком малом числе
сессий устойчивость оценки не доказана. Биномиальные интервалы сами по себе
не устраняют кластерную зависимость.

Для понимания масштаба: при нуле событий и независимых наблюдениях верхняя
односторонняя 95% граница равна `1 - 0.05^(1/n)`. Ноль порч на 3000 правильных
слов даёт около 0.1%; ноль неверных правок на 300 заменах — около 1%.
Это ориентир минимального объёма, не достаточное доказательство на зависимых
репликах. Маленький fixture-корпус не подтверждает безопасность.

После финальной проверки test любые изменения словаря, aliases, weights,
токенизации или порогов означают новую версию эксперимента. Повторно используемый
test становится регрессионным набором; для независимого вывода нужен новый holdout.

## Честное измерение производительности

Release build, фиксированные toolchain, commit, config, dictionary и dataset hashes.
Для сравнения индексов одинаковые distance semantics, K и scorer; отдельно
показывать число кандидатов и обрезаний. Не сравнивать FST Levenshtein с
SymSpell Damerau как эквивалентный поиск без приведения к общей метрике.

Каждый engine запускается отдельным процессом, чтобы пик памяти не накапливался
от предыдущего. Первый проход и минимум пять прогретых повторов; порядок engines
менять по зафиксированному seed. Не сбрасывать системный page cache привилегированными
командами. Первый процесс не называть гарантированно холодным дисковым кешем.

Отдельно измерять:

- build time и peak RSS сборки индекса, размер индекса;
- process startup, index load, первый запрос;
- tokenization, candidate generation (включая создание FST-автомата), scoring,
  decision и formatting;
- end-to-end latency строки и p50/p95/p99 времени токена;
- throughput всего файла, steady RSS и peak RSS, число токенов/слов/уникальных слов;
- cache off/on и 1/2/4 потока как отдельные конфигурации.

Не смешивать скорость с подробной JSONL-диагностикой и без неё; стоимость записи
review/debug измерять отдельно. Для mmap сохранять доступные показатели RSS и
page faults: размер адресного отображения не равен занятой физической памяти.
В отчёте указывать виртуальную машину и вариацию времени; p99 на сотне токенов
не выдавать за устойчивую оценку. Массовые 10k/100k/1M прогоны могут быть без gold,
но тогда они измеряют только производительность.

## Артефакты одного опыта

```text
rechprav/experiments/<id>/
  manifest.json       # git SHA + dirty state, версии, seed, hashes, команды, машина
  config.toml         # реально использованные параметры
  metrics.json        # числители, знаменатели, доли, интервалы, срезы
  timings.csv         # отдельные повторы, без усреднения до сохранения
  report.md           # гипотеза → метод → результат → ограничение → решение
```

Для приватного корпуса predictions/debug/review и конфиг с личными данными
находятся в ignored private-каталоге; публичный manifest ссылается на их хеши.
Generated индексы — в ignored artifacts; manifest сохраняет рецепт их построения.
Числовые отчёты не заполняются до запуска. Ошибка запуска фиксируется с причиной,
а не превращается в нулевую latency или нулевой FCR.

После опыта: обновить `docs/rechprav/history.md`, агрегированный `RESULTS.md`,
и статус компонента: принят / отклонён / недостаточно данных / отложен.
Для каждого сильного варианта сохранить разбор 20–50 ошибок или всех доступных.
Объяснение причины отмечается как гипотеза, если механизм не проверен ablation.
