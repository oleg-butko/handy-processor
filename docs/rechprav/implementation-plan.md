# Rechprav: поэтапная реализация

Статус: реализованы каркас, KEEP и первый OOV baseline B1 (trie + Levenshtein=1).
Проведено сравнение защит на технических примерах; качество на Handy ещё не оценено.
Дата: 2026-09-19. Основание: [исходный обзор](first-plan.md).
Методика измерений: [experiment-protocol.md](experiment-protocol.md).
История решений: [history.md](history.md). Текущее состояние: [RESULTS.md](RESULTS.md).

## Что должно получиться

Локальная Rust CLI в `rechprav/`, принимающая UTF-8 текст и создающая прежде всего
`review.txt`: исходная строка и только предложенные замены, связанные с позициями слов.
Опционально — `corrected.txt` и подробный JSONL. Сомнительные случаи остаются без изменений.
Исходный файл сохраняется; обработка не использует сеть.

Первый полезный результат — работающий просмотр с простым осторожным корректором
и воспроизводимой оценкой. Лучший алгоритм заранее неизвестен. Возможный итог —
обычный словарный поиск, если дополнительные компоненты не докажут пользу.

## Что обнаружено в существующем проекте

- Сервер написан на TypeScript; Rust уже используется в отдельном Tauri launcher.
- `src/transformation-rules.ts` применяет правила последовательно и синхронно:
  регистр → русские числительные → конечная точка. Новый процесс нельзя просто
  вставить в синхронный `apply` без проектирования взаимодействия.
- `src/russian-numerals.ts` уже содержит ограниченную коррекцию на одну правку
  внутри числовых конструкций. Это полезный пример осторожной политики,
  но его словарь и токенизация не покрывают общую коррекцию ASR.
- `original_text` и `transformed_text` в истории — вход и результат правил,
  а не ASR и вручную проверенный эталон. Экспорт содержит разделители и оба текста;
  его нельзя подавать как готовый файл «одна строка — один фрагмент».
- Пользователь подтвердил: пары ASR → правильный текст пока не подготовлены.
  Подготовка и ручная разметка реальной истории входят в первый этап.
- При продолжении работы Rust/Cargo найдены в `~/.local/bin`, с отдельными
  каталогами toolchain/cache в `~/.local/share/handy-processor-*`.
  Первичная проверка PATH и `~/.cargo/bin` была недостаточной. Установка не понадобилась.

## Архитектурные договорённости

```text
Исходные байты и границы строк
  → TextToken + lexical mapping + нормализованные ключи
  → защита неизменяемых участков
  → CandidateGenerator
  → CandidateScorer
  → DecisionPolicy: заменить / оставить
  → список правок по исходным диапазонам
  → review / corrected / debug
```

`Corrector` объединяет компоненты, но генератор, оценка и порог решения сменяются
независимо. Во всех сравнениях присутствует кандидат KEEP — исходное слово.
Высокий приоритет domain-словаря защищает термин и даёт кандидата, но сам по себе
не разрешает заменять обычное слово: `куда → CUDA` требует контекста.

Предлагаемые внутренние сущности:

- `TextToken`: тип, исходный UTF-8 byte range, ссылка на исходный текст.
- `LexicalToken`: стабильный индекс, диапазон TextToken, ключ поиска, признаки защиты.
  Слова, числа и защищённые атомы вроде URL занимают позиции; чистая пунктуация — нет.
- `Edit`: полуоткрытый диапазон lexical tokens, исходный byte range, replacement.
  В первой версии допускается только 1→1, но представление рассчитано на диапазоны.
- `Decision`: original, candidate, KEEP score, candidate score, margin, features,
  alternatives, reason и nullable confidence. Пока нет калибровки, confidence — null:
  сумма весов не называется вероятностью.

NFC, нижний регистр и настройка е/ё применяются к ключам сравнения, не к исходнику.
Неизменённые байты, пробелы, пунктуация и окончания строк сохраняются в corrected.
Обычный и верхний регистр восстанавливаются; смешанный регистр по умолчанию защищён.
`ignore.txt` запрещает изменение независимо от других признаков.
URL, пути, команды, числа, версии, латиница, смешанные идентификаторы и короткие
слова ≤3 символов защищены в первоначальном режиме. Капитализация — признак риска,
а не надёжный детектор имён: начало предложения нужно проверять отдельно.

Review использует один диапазон токенов для пары SOURCE/CHANGES, с учётом ширины
обеих строк. Единица ширины — отображаемая колонка; отдельно проверяется лимит
130 Unicode scalar values. Табуляции и управляющие символы отображаются безопасно.
Обычные переносы — между словами, по возможности на границах предложений.
Для единственного токена длиннее 130 действует отдельный режим продолжения:
визуальные фрагменты имеют один token id и номер части, границы по графемам;
единственный маркер/замена выводится на первой части, остальные обозначены как
продолжение. Новых lexical positions это не создаёт. Число частей определяется
по более длинной стороне пары. Для экстремальной графемы длиннее лимита используется
экранированное представление. Полный исходник всегда доступен через byte ranges в JSONL.
Эти случаи должны быть явно покрыты golden tests, включая изменение длины замены.

## Этапы и контрольные точки

Каждая пронумерованная подзадача — небольшой законченный результат; этап закрывается
после проверки, сохранения артефактов и записи решения, а не после написания кода.

### 0. Зафиксировать постановку и исходное состояние

1. Прочитать обзор, проверить текущий pipeline, формат экспорта и доступные инструменты.
2. Сохранить план, протокол экспериментов и начальный отчёт.
3. Зафиксировать наличие реальных данных. Пользователь подтвердил отсутствие
   готовых пар; инфраструктуру разрабатывать на технических fixtures,
   но не объявлять качество на синтетике качеством на Handy.

Выход: настоящий комплект документов и `rechprav/experiments/000-inventory/`.
Обследование выполнено; необходимость подготовки размеченного корпуса подтверждена.

### 1. Корпус и честная оценка — до выбора алгоритма

1. Подготовить Rust toolchain; зафиксировать версии. Системные установки требуют
   отдельного согласования согласно правилам проекта; пока ничего не устанавливалось.
2. Создать самостоятельный Cargo package в `rechprav/`, отдельно от launcher;
   зафиксировать Cargo.lock, добавить форматирование, тесты и CLI `--help`.
3. Описать JSONL-корпус и валидатор: id, session/group, ASR model (если известна),
   source, gold, expected edits, tags, provenance, annotation status.
4. Подготовить импорт исходных фрагментов истории. Многострочные записи сохранять
   одной JSONL-записью; не угадывать границы по пустым строкам. Для штатного экспорта
   учесть его разделители и неоднозначность при их наличии в тексте; предпочтителен
   структурированный экспорт с id. `transformed_text` не считать gold.
5. Собрать 50–100 технических fixtures: пунктуация, NFC, е/ё, регистр, C++, URL,
   пути Windows/Linux, дефисы, версии, пустые строки, CRLF, длинные токены.
6. Начать разметку с 300–500 реальных фрагментов, сохраняя правильные строки.
   Это объём пилота, не достаточное доказательство безопасности. Неоднозначные
   случаи помечать отдельно; без аудио не выдумывать, что было произнесено.
7. До настройки разбить по сессиям и группам дубликатов на train/dev/test.
   Начальная пропорция 60/20/20, корректируется до экспериментов по объёму данных.
8. Реализовать scorer метрик и KEEP baseline, проверить формулы на ручных примерах.

Готово, когда корпус валидируется, разбиения не пересекаются, KEEP ничего не меняет,
метрики имеют понятные знаменатели. При нехватке данных остаётся статус «пилот».

### 2. Минимальный рабочий просмотр и простой baseline

1. Reader, tokenizer, mapping, нормализация ключей и точное восстановление текста.
2. Formatter ≤130 и JSONL с диапазонами; безопасное создание отдельных outputs
   без перезаписи входа, включая совпадающие пути через symlink/hardlink.
3. `dictionary.txt`, отдельные частоты, `domain.txt`, `ignore.txt`; небольшой
   проверенный fixture-словарь для correctness, затем полный словарь словоформ.
4. `build-dict`, `correct`, `inspect`, `benchmark`: минимальные рабочие команды.
5. KEEP и B1: обычный Unicode Levenshtein, сначала distance=1, только OOV.
   Для рабочего поиска — trie с отсечением DP; полный перебор допустим только
   как эталон на маленьком словаре в тестах.
6. B2: тот же генератор + ограниченный log-frequency prior + сравнение с KEEP
   и вторым кандидатом. Все веса, лимиты и пороги в TOML.
7. Отдельные опыты: distance=1/2, частота включена/выключена, domain включён/выключен,
   защита коротких слов и имён. Каждый раз изменять один фактор.

Готово, когда реальные входы дают удобный review, нет потерь текста и есть таблица
KEEP/B1/B2 с примерами правильных и ложных предложений. Это первая полезная версия.
Пока она служит просмотру; интеграция в автоматическую вставку отложена до оценки.

### 3. Выбрать генератор: trie / SymSpell / FST

1. Зафиксировать одинаковые словарь, нормализацию, лимит K, scorer и decision policy.
2. Реализовать SymSpell adapter с Unicode strategy; проверить полноту на маленьком
   словаре против полного перебора, а также тип edit distance конкретной реализации.
3. Реализовать FST adapter: отдельно измерить построение автомата, обход индекса
   и полный lookup. Затем сравнить загрузку в память и mmap.
4. Первый честный опыт — общий обычный Levenshtein, distance 1/2. Если SymSpell
   использует Damerau/OSA, проверить полноту генерации и фильтровать общей метрикой;
   дополнительные перестановки оценивать отдельным опытом. Одинаковое число `2`
   при разных расстояниях не означает одинаковую задачу.
5. Измерить candidate recall@1/3/5/10/20, полный recall до ограничения K,
   p50/p95/p99 lookup, throughput, startup, RSS/peak RSS, размер и сборку индекса.
6. Проверить длинные слова, плотные группы соседей, ошибки автомата и большие
   фонетические корзины в дальнейшем. Лимиты должны приводить к KEEP с reason.

Выбор: минимальная стоимость при достаточной полноте кандидатов; проигравший
генератор может остаться сравнительным вариантом. FST не является априори лучшим
и SymSpell не является самостоятельным доказательством качества исправления.

### 4. Проверить пользу фонетики

1. Weighted edit как reranker на неизменном наборе кандидатов. Различать обычный
   Levenshtein, OSA и полный Damerau; назвать реализованный вариант точно.
2. Ручные стоимости оглушения/озвончения и гласных вынести в TOML. Сравнить с B2
   при одинаковом ограничении FCR. Проверить е/ё и сохранение редких слов.
3. Добавить простой phonetic key только как дополнительный источник кандидатов.
   Сравнить: базовый поиск; weighted; phonetic; weighted + phonetic.
4. Измерить прирост candidate recall и цену новых ложных предложений отдельно.
   Часть дешёвых фонетических правок может выходить за обычный edit-radius:
   изменение scorer само по себе не расширяет кандидатов.
5. Только при оставшейся проблеме полноты проверить Russian Soundex/Metaphone,
   затем G2P/eSpeak NG; заранее проверить лицензии. Для G2P продумать и стоимость
   фонетизации неизвестного входного слова: таблицы словаря для этого недостаточно.

Оставить компонент при измеримом выигрыше на dev и сохранении ограничений по вреду.
При росте коллизий без полезного прироста — отклонить или использовать только для inspect.

### 5. Модель ошибок конкретного ASR — если хватает пар

1. На train выровнять gold → recognized, сохранить источник/модель ASR.
2. `train-confusions`: направленная P(recognized | correct), с корректным
   знаменателем, неизменёнными событиями, вставками, удалениями и smoothing.
3. Сначала 1→1, затем 1→2/2→1/2→2 на уровне символов; не смешивать это с границами слов.
4. Сравнить ручные веса, обученные веса и fallback к ручным при редких событиях.
5. Оценить на других сессиях; если возможно — на другой версии ASR. Проверить,
   что модель не запомнила несколько часто повторяемых слов.

При недостатке наблюдений этап отложить с указанием числа событий. Небольшое число
примеров не оправдывает уверенные learned costs. Контекст можно исследовать независимо.

### 6. Контекст и ошибки в существующих словах

1. Сначала локальная сглаженная bigram-модель, затем trigram при доказанном выигрыше.
   Источники текста и их пересечения с тестом должны быть известны.
2. Сравнивать изменение вероятности всей затронутой локальной цепочки n-грамм
   слева и справа относительно KEEP; не удваивать вклад одних и тех же переходов.
3. Сначала контекстный reranking OOV. Затем отдельный режим real-word с более
   строгими порогами и своим отчётом о ложных заменах правильных слов.
4. Проверить доменные пары: `куда → CUDA`, омонимы и обычные употребления `куда`.
   Сам domain dictionary не даёт знания о звучании: нужны явно заданные варианты
   распознавания либо отдельная генерация межалфавитных кандидатов и контекст.
5. Сравнить простой локальный scorer с KenLM, если размеры/скорость оправдывают
   зависимость; JamSpell — факультативный внешний локальный baseline.
6. Сначала все решения оценивать по исходной строке, без каскада уже внесённых правок.
   Совместный выбор нескольких замен исследовать только на выявленных конфликтах.

Если контекст портит имена или нормальные фразы, оставить его только для ранжирования
OOV либо отклонить. Real-word режим не включать по результатам одних примеров.

### 7. Минимальный гибрид и подтверждение результата

1. Собрать только выигравшие компоненты; выполнить ablation каждого из них.
2. Настроить пороги на dev; калибровку при достаточном объёме делать на выделенной
   части dev или out-of-fold, отделяя её от подбора весов. Построить risk/coverage curve.
3. Зафиксировать конфиг, версии и shortlist до единственного итогового сравнения на test.
4. Разобрать 20–50 ошибок каждого сильного варианта, либо все ошибки, если их меньше.
   Разбор test делать после фиксации результата; новые правки требуют нового holdout.
5. Сравнить с лучшим одиночным методом и B2 при одинаковом ограничении FCR.
6. Оставить один профиль по умолчанию. FAST/BALANCED/QUALITY добавлять только
   при существенных, воспроизводимых различиях на Pareto frontier.

Готово, когда есть воспроизводимый RESULTS с доверительными интервалами,
ограничениями данных и списком принятых/отклонённых компонентов. «Данных недостаточно»
— допустимый исследовательский вывод, но не основание включать автокоррекцию.

### 8. Производительность и интеграция с Handy

1. Профилировать tokenizer / lookup / scoring / LM / formatter отдельно.
2. По одному проверить reusable buffers, компактные IDs, bounded candidate cache,
   mmap, затем многопоточность. Ключ контекстного кэша включает контекст и версии ресурсов.
3. Сравнить 1/2/4 потока, повторяемые и уникальные слова, короткие интерактивные запросы
   и 10k/100k/1M токенов для throughput. Порядок и решения должны совпадать.
4. Сначала интеграция в режиме просмотра предложений. Затем опциональное правило,
   выключенное по умолчанию до выполнения критериев. Выбрать механизм вызова по
   измерениям; постоянный локальный subprocess с JSONL — первый кандидат, без HTTP.
5. Проверить запуск/завершение процесса, таймаут, недоступный/повреждённый словарь:
   при ошибке возвращать исходный текст и диагностировать причину.
6. Порядок «коррекция → числительные → регистр/пунктуация» проверить отдельно:
   ранний lowercase теряет признаки имён; текущую семантику существующих правил
   менять только с regression tests и сравнением результата целого pipeline.
7. Проверить упаковку и работу без сети на Debian и целевой Windows-сборке.

До измерения бюджета времени/памяти по реальному использованию абсолютные лимиты
не выдаются за требования пользователя. Начальный performance-budget фиксируется
после B2, до сравнения тяжёлых компонентов; превышение требует обоснованной пользы.

### 9. Отдельные поздние эксперименты

CompoundCorrector 2→1/1→2 — отдельный режим, span-метрики и формат review;
начинать только если такие ошибки заметны в корпусе. Пунктуация остаётся отдельной
задачей. Небольшая локальная neural model — только после анализа устойчивых ошибок
классических методов. Их отсутствие в первой версии не блокирует выпуск CLI.

## Как выбирать оптимальное решение

Начальная гипотеза требований для автоматического режима: precision ≥99% и
FCR ≤0.1% (не более одного испорченного правильного слова на тысячу).
Это предлагаемые ориентиры, не измеренные результаты и не обещание.
Смотреть не только точечные значения, но и односторонние 95% границы:
нижнюю для precision, верхнюю для FCR. При малой выборке — продолжать сбор данных.

Среди прошедших ограничение вариантов сравнивать уменьшение WER, число полезных
исправлений на 1000 слов, recall/F0.5, затем latency, память и сложность поддержки.
KEEP нужен как нулевая точка, но не может выиграть как полезный корректор без
исправлений и улучшения WER. Recall считать и по всем lexical errors, и отдельно
по поддерживаемым 1→1 — нельзя улучшать отчёт исключением сложных ошибок.

При статистически неразличимых результатах предпочесть более простой вариант.
Для сомнительных предложений допустим отдельный исследовательский вывод в inspect,
но он не смешивается с precision основного review и автоматическими заменами.

## Порядок ближайшей работы

Первый небольшой цикл: toolchain → fixtures/JSONL validator → tokenizer/KEEP →
formatter → метрики → пилот реальных данных → B1/B2. Следующий цикл: общие
кандидаты и честное сравнение trie/SymSpell/FST. Только затем weighted/phonetic.
Сбор и разметку реальных данных вести с начала, чтобы готовый код не ждал benchmark.

Текущий прогресс: toolchain, 67 tokenizer fixtures, 12 синтетических записей,
JSONL validator, tokenizer, KEEP, formatter и контрольные метрики реализованы.
Пользователь попросил пока использовать технические примеры: реальный пилот
отложен, этап 1 целиком не закрыт. Общий импорт истории, автоматическое групповое
разбиение и метрики произвольных предсказаний ещё предстоят. Следующая небольшая
подзадача после этапа 001 была выполнена: словари/защита, TOML, `build-dict`,
`correct`, кандидаты в `inspect` и индексированный OOV baseline distance=1.

Этап 002: на 27 синтетических записях сравнили KEEP/B1 и отключения отдельных
защит. B1 исправил 9 ошибок и сделал 2 неверные замены; единственный кандидат
не гарантирует полезность. Защиты оставлены; итоговые данные и все оставшиеся
ошибки находятся в `rechprav/experiments/002-baseline/`.
Следующий шаг — независимый полный словарь словоформ и затем частоты/B2;
полноценный этап 2 пока не закрыт. Подбор порогов по реальной истории и интеграция
остаются за пределами выполненного технического опыта.

Ветки: `feat/rechprav-foundation`, `feat/rechprav-baseline`, затем отдельная ветка
для каждого опыта. Коммит после работающей подзадачи: например,
`feat(rechprav): add lossless tokenizer` или `test(rechprav): verify correction metrics`.
Результат опыта связывается с точным commit, config и хешами данных; неудачный
подход сохраняется в истории и своей ветке, но не обязан оставаться в runtime.

## Проверенные первичные источники

Проверены 2026-09-19; это сведения о доступных механизмах, а не результаты наших опытов.

- [SymSpell автора](https://github.com/wolfgarbe/SymSpell): symmetric deletes и режимы
  выдачи кандидатов. Опубликованные ускорения не переносим на русский ASR-корпус.
- [Rust symspell](https://docs.rs/symspell/0.5.2/symspell/): есть UnicodeStringStrategy;
  пример использует ASCII. Конкретный crate/версия будут закреплены после проверки.
- [fst](https://docs.rs/fst/0.4.7/fst/): сортировка ключей при сборке, возможность mmap.
  [Levenshtein](https://docs.rs/fst/0.4.7/fst/automaton/struct.Levenshtein.html) работает
  с Unicode scalar values, но создание автомата отмечено как экспериментальное
  и потенциально затратное. Из этого следует необходимость полного lookup benchmark.
- [Hunspell](https://github.com/hunspell/hunspell): проверять конкретный русский
  словарь и его аффиксы; лицензия движка не заменяет лицензию данных.
- [KenLM](https://github.com/kpu/kenlm): кандидат для отдельного контекстного этапа.
- Страницы OpenCorpora `https://opencorpora.org/dict.php` и `?page=downloads`
  инструментом просмотра получить не удалось. Источник словоформ, актуальный архив,
  лицензию и частотные ресурсы нужно проверить до скачивания и выбора словаря.

Сеть использовалась только для чтения технической документации. Runtime и benchmark
должны работать на заранее подготовленных локальных ресурсах; тексты ASR в сеть не отправляются.
