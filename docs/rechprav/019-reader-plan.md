# 019: время жизни загруженного engine (до реализации)

Дата: 2026-09-22, продолжение публикации 018.

Проверить отдельный Rust reader в экспериментальном контуре. Снимок SQLite
передаётся ему как JSON; сервер и UI пока не подключать. Тот же replay validator
должен возвращать созданный TermEngine: проверяются именно удерживаемые в памяти
байты ресурсов, без второй загрузки после проверки и без повторного открытия
словари/конфига для каждого текста.

Состояния: нет engine; активный engine; новая цель/загрузка; ошибка новой загрузки
при сохранённом старом engine. Разделить observe → prepare → install. Observe
отмечает самое новое desired/active поколение; install повторно сверяет ticket.
Поздний prepare не может заменить более новое наблюдённое поколение даже при
ошибке его загрузки. Повтор того же снимка не должен сбрасывать/перезагружать engine.

Начатый запрос получает собственный handle на engine и generation. После reload
его результат по-прежнему относится к прежнему поколению; новые handles видят
новый engine. В текущей библиотеке dyn CandidateGenerator не имеет Send/Sync:
сначала проверяем Rc ownership и чередование операций на одном потоке, не выдаём
это за проверку многопоточного HTTP-сервера. Изменение trait/runtime и process
bridge — отдельные решения перед интеграцией.

Зафиксированные проверки:

1. Первый профиль; выключенный профиль; повтор без reload; no-active/ошибка первой
   загрузки явно недоступны, без неявного возврата непроверенной коррекции.
2. Старый handle до reload сохраняет старый ответ и generation; после освобождения
   последнего handle старый engine уничтожается.
3. Подготовить два кандидата, установить в обратном порядке: старый запрещён.
4. Ошибка нового профиля сохраняет старый engine, но не разрешает старый ticket.
5. Регрессия desired/active, та же generation с другими bytes, другой scope — отказ.
6. Изменение/удаление ресурсов до reload — отказ; после успешной загрузки уже
   начатые и новые запросы к этому engine работают без доступа к изменённым файлам.
7. Подмена snapshot/receipt/hash — отказ; replay по-прежнему обязателен.
8. На прежних 20 dev строках результаты до/после переключения совпадают с 017/018;
   профиль выключения даёт KEEP. Алгоритм/веса не перенастраивать.

Артефакты/история сохраняются в стандартных rechprav/experiments и docs/rechprav.
