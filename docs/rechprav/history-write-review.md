# Ревью записи истории распознаваний

2026-09-26. Проверены пути записи и чтения истории, обработка HTTP-запросов,
настройки правил и жизненный цикл корректора. Существенная задержка найдена
в сохранении каждого распознавания; изменений алгоритма коррекции нет.

**P2 — время добавления росло с лимитом истории.** После каждого `INSERT`
выполнялся запрос, ищущий запись с `OFFSET maxEntries` в обратном порядке.
Даже когда история ещё не заполнена, SQLite проходил десятки тысяч ключей;
на лимите 50 000 это происходило при каждом распознавании. Поскольку SQLite
используется синхронно, запрос задерживал и другие HTTP-операции.

Теперь внутри той же транзакции сначала считается число записей. Если оно
выше лимита, удаляется ровно превышение, начиная с самых старых ID. Поиск
старого ID через `OFFSET maxEntries` больше не выполняется. При изменении
лимита тоже удаляется только превышение. Порядок истории, точный лимит и
поведение при пропусках ID сохранены; схема БД не менялась.

На технической истории из 50 000 записей 1000 вставок в SQLite `:memory:`
заняли 989 мс до изменения и 64 мс после него (около 15 раз быстрее).
Полное сохранение через `TransformationLog.add()` в файловую временную БД:
при 49 000 исходных записях следующие 500 заняли 2175 → 1590 мс, а
следующие 2000 на полном лимите — 8207 → 6064 мс. Это одиночные локальные
замеры: запись транзакций на диск ограничивает общий выигрыш, а время на
другой машине может отличаться. Скрипт с обеими SQL-стратегиями и его вывод
находятся в [артефактах](../../rechprav/experiments/028-additional-review/report.md).

Кешировать число строк в памяти решено не делать: отдельное соединение с
SQLite может изменить историю, и такой кеш неверно удерживал бы лимит.
Новый запрос `COUNT(*)` выполняется на каждой вставке, но в замере он дешевле
прежнего прохода до позиции `maxEntries`. Поиск подстрок в истории всё ещё
сканирует записи; ускорение его нормализации описано в
[предыдущем ревью](history-search-review.md). Для миллиона записей и на
Windows время пока не измерялось.

Проверки: 103 серверных теста, включая новые регрессии на массовую обрезку,
пропуски ID и запись через второе SQLite-соединение; `npm run typecheck`;
`git diff --check`. Тесты и замеры
использовали только временные или in-memory базы, рабочая история не менялась.
