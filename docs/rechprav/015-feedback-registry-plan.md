# 015: принятие предложений и отзыв подтверждений

Зафиксировано 2026-09-22 до реализации. Продолжение 014, только offline.
Корпус прежний: 28 synthetic/dev строк feedback-drafts; качество на независимом
ASR не измеряется. Новая переменная — жизненный цикл принятого правила.

## Гипотезы и выбор

1. Принятие только по стабильному proposal id опасно: после отмены всех evidence
   новое событие с той же парой возвращает тот же id и оживляет старое решение.
   Выбран пересчёт по пересечению текущих evidence и evidence, показанных при
   принятии. Хотя бы одно одобренное подтверждение должно оставаться активным.
2. Отдельный append-only JSONL решений accept/reject/disable, последнее уникальное
   решение на (scope, proposal id) определяет состояние. Повтор одного decision id
   идемпотентен; разные payload с тем же id — ошибка. Включение после disable/reject
   требует нового accept. Накопления веса нет.
3. Решение ссылается на checkpoint: длина префикса журнала correction/retract,
   SHA256 его нормализованного JSON и environment fingerprint. Предложение и его
   evidence восстанавливаются из этого префикса, а не принимаются на веру из JSON.
   Редактирование/сокращение исторического префикса — ошибка; дописывание допустимо.
4. Environment включает исходный пользовательский config, ресурсы baseline и
   исходники сборки инструмента. При его изменении старое принятие stale и требует
   нового review. Это намеренно консервативно, даже правка комментария может
   потребовать повторной проверки. SHA не является подписью или авторизацией.
5. Непринятый конфликт не входит в активный профиль. Два принятых конфликтующих
   правила передаются существующему механизму ambiguity/KEEP без выбора победителя.
   Другой scope, другой контекст или новый id не наследуют принятие.

## Маленькие подзадачи

1. Зафиксировать сценарии до реализации в scripts/registry_profiles.py.
2. Отдельный helper/example: review tokens, строгая проверка решений/checkpoints,
   отчёт состояний, активный config только из текущих принятых правил. Без записи
   в рабочий профиль/словарь и без изменений runtime.
3. Тесты отмены/повтора/возвращения, конфликтов, чужого scope, подмены префикса,
   несуществующего proposal, изменения окружения и ограничений входа.
4. Прогнать frozen сценарии на прежних 28 строках. Проверить активные id и состояния,
   точное совпадение принятого профиля с 014 и независимые span-метрики.
   Сохранить inputs, outputs, manifests, команды и hashes.
5. Документировать ограничения и следующий этап захвата событий редактора.

Лимиты: 10000 correction/retract событий (унаследовано), 1024 строк решений,
32 различных исторических checkpoint lengths, 64 пары (checkpoint, scope).
Оба входных файла ≤64 MiB. Все проверки до создания нового output directory;
существующий каталог не перезаписывать. Это пересобираемый снимок, а не служба:
изменение журнала само по себе не обновит уже загруженную внешним приложением копию.

Критерии: без accept нет активных правил; последний отзыв одобренного evidence
убирает правило; повторное появление не активирует старое принятие; частичная
отмена оставляет правило при другом одобренном evidence; scopes изолированы;
принятый профиль повторяет 014 без улучшения заявленного качества.
